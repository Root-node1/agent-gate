4. Authentication dependencies

The baseline integrates AUTH-01 (email/password signup & login via django-allauth Headless, CSRF, mandatory email verification, the GET /api/auth/user/ endpoint). The remaining auth tasks (AUTH-02 through AUTH-06) are documented in docs/authentication-architecture.html but not yet implemented — they exist as a task decomposition for future work.

Auth task dependency graph

AUTH-01: Email/password signup/login  (DONE — c35287d in baseline)
   │
   ├── AUTH-02: Email verification + secure logout  (depends on AUTH-01)
   │    │
   │    ├── AUTH-03: Password reset & change  (depends on AUTH-02)
   │    └── AUTH-05: TOTP 2FA — enrollment, recovery codes, enforcement (depends on AUTH-02)
   │         │
   │         └── AUTH-06: RBAC + rate limiting  (depends on AUTH-05)
   │
   └── AUTH-04: GitHub OAuth  (depends on AUTH-01; connects to AUTH-05 for post-login 2FA)

GitHub OAuth (feat/github-oauth)

Depends on: AUTH-01 (allauth installed and configured in baseline).

  • Existing configuration: django-allauth with allauth.account and allauth.socialaccount in INSTALLED_APPS; AllauthMiddleware active; ACCOUNT_EMAIL_VERIFICATION = "mandatory".
  • Setup required: register a GitHub OAuth App (callback /accounts/github/login/callback/), set SOCIALACCOUNT_PROVIDERS["github"], configure DJANGO_GITHUB_CLIENT_ID / DJANGO_GITHUB_CLIENT_SECRET env vars (server-side only).
  • Email verification: SOCIALACCOUNT_EMAIL_VERIFICATION = "mandatory" must be enforced; GitHub emails that are unverified should not gain dashboard access.
  • Account linking: when a GitHub user matches an existing User.email, allauth should link the SocialAccount rather than create a duplicate; a custom SocialAccountAdapter enforces the allowlisted-domain rule.
  • Session/CSRF: OAuth completes server-side via Django sessions; the frontend reads the resulting sessionid/csrftoken cookies and then polls GET /api/auth/user/. No frontend token exchange.
  • Conflict risk: backend/config/urls.py extends the allauth URL includes — must be merged after the CRUD URL block already present in the baseline.

Account recovery (feat/account-recovery)

Depends on: AUTH-02 (email backend + verification flow).

  • Password reset: uses allauth ACCOUNT_PASSWORD_RESET; links expiring (1 hour, single-use) via ACCOUNT_PASSWORD_RESET_TIMEOUT = 3600.
  • Password change: POST /accounts/password/change/ requires the current password.
  • Email verification: reuses the AUTH-02 confirmation flow; ACCOUNT_EMAIL_CONFIRMATION_EXPIRE_DAYS = 3.
  • Session invalidation: logout (allauth POST /accounts/logout/) destroys the session row so a subsequent GET /api/auth/user/ returns 401. Password-reset flows should not rotate the session cookie unless the password is actually changed.
  • Shared files: settings (base.py), apps/accounts/adapters.py (custom AccountAdapter).

TOTP 2FA (feat/totp-2fa)

Depends on: AUTH-05 task unit; builds on AUTH-02's email flow + AUTH-06's rate limiting.

  • django-allauth MFA vs. django-two-factor-auth: the architecture doc recommends django-two-factor-auth (built on django-otp); this must be confirmed with the Tech Lead (see §11).
  • Enrollment: generate a TOTP secret, render a QR code (otpauth:// URI), verify a 6-digit code.
  • Recovery codes: 10 single-use backup codes (20 chars each) stored hashed at apps/accounts/models.py (new TOTPRecoveryCode model → shared-file risk with accounts app).
  • Enforcement: admin and approver roles are forced through the 2FA state machine; viewer is opt-in.
  • GitHub OAuth interaction: after a successful OAuth login, if the user has 2FA enrolled, redirect to GET /2fa/verify?prompt=1 before granting dashboard access.
  • API permission: 2FA status is surfaced via GET /api/auth/user/ (two_factor_enabled boolean) so the frontend can gate routes.
  • State machine: Unauthenticated → Primary Verified → Second Factor Required → Second Factor Verified → Authenticated Dashboard User.

5. Frontend dependencies

The React + TypeScript + Vite dashboard (frontend/) currently has two data paths (see docs/integration-gap-analysis.html):

  • 11 of 17 dashboard screens read from an in-memory demo store (frontend/src/demo/store.ts) — zero real backend calls.
  • 3 simulator/live pages call the real agent API (POST /v1/spend-requests/) via frontend/src/api/spendRequests.ts using an in-memory agent key.

Critical finding

The dashboard is a fully functional mock application. It replicates the backend rule engine in TypeScript but has no integration with the actual backend for any dashboard operation (approvals, policies, agents, audit, transactions, settings).

Frontend integration dependencies

CSRF cookie bootstrap
Must call GET /api/auth/headless/browser/v1/config to obtain the CSRF cookie before any state-changing request.
Session-aware requests
All dashboard fetch() calls must use credentials: "include" and pass the X-CSRFToken header.
Dashboard auth flow
SessionProvider.tsx currently stores only an agent key; it must be extended to hold the dashboard user and roles from GET /api/auth/user/.
API client split
spendRequests.ts (agent-key path) must NOT be modified; a new dashboard API client must be added alongside it.
Contract mismatches
Policy list response uses UUID + minor currency units + merchant_rules[]; the frontend demo type uses numeric IDs + major units + split allowed_merchants/blocked_merchants. A response transformer is required.
Agent key auth
frontend/src/api/spendRequests.ts + AgentKeyAuthentication backend are already wired — the simulator path is independent and unchanged by auth work.

6. Backend and infrastructure dependencies

Gemini chatbot (feat/gemini-chatbot)

  • Depends on: dashboard session auth (admin/approver can invoke), the spend/policy read APIs for context.
  • Security boundary: read-only advisory proxy; must remain read-only; server-side Gemini key only.
  • Shared files: backend/config/urls.py (new /v1/gemini/… include), requirements.txt (google-generativeai), frontend/src/session/ + App.tsx (protected route).

Background jobs (feat/background-jobs)

  • Depends on: dashboard auth (admin-only management endpoints), the approvals engine (to schedule expiry checks).
  • Tech stack: Procrastinate (Postgres-backed queue), per docs/implementation-plan.html.
  • Shared files: requirements.txt (procrastinate), config/settings/base.py (task queue config), backend/run.sh (worker startup), apps/approvals/services.py (expiry scheduling).
  • Blocker for staging: expire_approvals must run automatically (P1).

PayPal sandbox (feat/paypal-sandbox)

  • Depends on: the spend-request engine, the approval flow (only approved requests execute), the audit log.
  • Security boundary: sandbox-only; no production financial execution; no PayPal credentials committed to Git.
  • Required env vars: PAYPAL_CLIENT_ID, PAYPAL_CLIENT_SECRET, PAYPAL_WEBHOOK_SECRET (sandbox credentials only).
  • Shared files: requirements.txt (PayPal SDK), config/urls.py (webhook endpoint), apps/payments/executors.py, apps/approvals/views.py (post-approve trigger).

Contabro VPS deployment (infra/contabo-deployment)

  • Depends on: all application features being on main or a release candidate; a Docker Compose stack.
  • Topology: Caddy (HTTPS) → Gunicorn → Neon PostgreSQL; static assets served by Caddy.
  • Shared files: docker-compose.yml, Caddyfile, backend/config/settings/prod.py (allowed hosts, secure cookie flags).
  • Critical: must be the last integration — it depends on auth, CRUD, approvals, PayPal, and background jobs all being stable.

PostgreSQL migrations

  • Baseline verification: makemigrations --check --dry-run reports no missing migrations.
  • Any new model (e.g., TOTP recovery codes, invite codes) must ship its migration alongside its code; migrate --plan should be re-run after each feature lands.
  • The audit AuditEvent model already has an append-only DB trigger (commit 973f5a6); new audit event types must extend the trigger, not bypass it.

CI and integration testing

  • The GitHub Actions workflow (.github/workflows/ci.yml) runs backend tests against PostgreSQL, the frontend build, and a security audit.
  • After each feature branch is rebased onto the baseline, CI must run before any merge — baseline is 339 passing tests; regressions are not acceptable.
  • No frontend unit/E2E tests exist; the first priority after auth is adding them (P1 in the gap analysis).

9. Safe future integration strategy

Guiding rules for bringing each feature onto the validated baseline:

  1. Never rebase integration/auth-crud. It is the reference baseline. Treat 3d6fef9 as an immutable anchor.
  2. Rebase each feature branch onto 3d6fef9 before merge. Because all pending branches derive from bc6987e with no unique commits, a rebase is a fast-forward that cannot lose work.
  3. Integrate in dependency order (§8). Auth tasks must land before the dashboard or PayPal work that consumes sessions.
  4. Run the full gate after each integration: 
    python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
ruff check .
git diff --check
    Regression threshold: 339 passing, 2 skipped — no new failures.
  5. Re-run the INT-01 compatibility tests after every auth change. The 6 cross-module integration tests verify that auth and CRUD layers remain mutually compatible.
  6. Keep backend/engine/ untouched by auth/infra changes (enforced by .importlinter).
  7. Do not merge auth + CRUD + dashboard into main until the frontend gap (demo store → real API clients) is closed for at least the P0 screens.

10. Approval gates

Before merging, pushing, or deploying

The following actions require explicit Tech Lead approval before proceeding:

  • Rebaselining any feature branch onto integration/auth-crud.
  • Merging a feature branch into main or into integration/auth-crud.
  • Adding production PayPal credentials or switching PayPal from sandbox to live.
  • Changing Cloudflare tunnel/routing configuration.
  • Introducing new third-party dependencies (auth libraries, queue, PayPal/Gemini SDKs).

No merge, rebase, cherry-pick, push, or deploy is performed in INT-02 itself.
