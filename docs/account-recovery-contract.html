2.2 Two reset modes: token-link (default) vs code

allauth 65.21.0 supports two password-reset mechanisms, selected by ACCOUNT_PASSWORD_RESET_BY_CODE_ENABLED (default False):

  • Token-link flow (default, False): the reset email contains a link embedding key = <uidb36>-<token>. The SPA reads key from the link and POSTs it back to auth/password/reset. The token is a stateless, timestamped hash (Django PasswordResetTokenGenerator), so nothing is stored.
  • Code flow (True): a one-time code is emailed and entered in the SPA; confirmation uses PasswordResetVerificationProcess with PASSWORD_RESET_BY_CODE_TIMEOUT (default 180s) and PASSWORD_RESET_BY_CODE_MAX_ATTEMPTS (default 3). Template password_reset_code_{subject,message}.

AUTH-01 does not set PASSWORD_RESET_BY_CODE_ENABLED, so the token-link flow is the configured mechanism. AUTH-02B should preserve the default token-link flow and avoid switching to the code flow (it would add a session-bound stage process for no security gain over correctly-expiring stateless tokens).

2.3 ⚠ Correction: ACCOUNT_PASSWORD_RESET_TIMEOUT does not exist

docs/integration-dependency-plan.html (line “Password reset”) and docs/authentication-architecture.html (AUTH-03) both cite ACCOUNT_PASSWORD_RESET_TIMEOUT = 3600. This setting does not exist in allauth 65.21.0. A grep of the entire allauth 65.21.0 wheel for PASSWORD_RESET_TIMEOUT returns zero matches.

Token expiry for the (default) token-link flow is governed entirely by Django’s own django.contrib.auth.tokens.PasswordResetTokenGenerator, which reads settings.PASSWORD_RESET_TIMEOUT (seconds). Its default is None, in which case Django does not enforce a time bound — reset links effectively never expire. Therefore:

  • AUTH-02B must add PASSWORD_RESET_TIMEOUT = 3600 to config/settings/base.py (Django setting, not an ACCOUNT_ setting).
  • Single-use is already guaranteed by allauth/Django: the token hash embeds the current password hash, so check_token() returns False once the password is changed. Reusing a consumed link is rejected with the same invalid_password_reset error as an expired/invalid one.
  • Multiple outstanding tokens can coexist until one is used; this is acceptable and bounded by the IP + per-email rate limits.

2.4 UUID primary-key compatibility

AgentGate’s User (backend/apps/accounts/models.py) uses a UUIDField primary key. allauth 65.21.0 supports this: user_pk_to_url_str (allauth/account/utils.py) returns user.pk.hex for UUID PKs, and url_str_to_user_pk reconstructs it via the field’s to_python. The reset URL uidb36 segment is therefore a 32-hex-char UUID — no custom UID encoding is needed and existing allauth code paths work unchanged.

2.5 Non-headless accounts/ surface to be narrowed

AUTH-01 mounts allauth.account.urls at /accounts/ but strips only password/change (via _without_password_change in config/urls.py). The non-headless password-reset routes (password/reset/, password/reset/key/.../, etc.) are HTML-form endpoints, not JSON, and must not be used by the SPA. AUTH-02B should extend the existing filter to also exclude the non-headless password-reset routes (they are redundant now that the Headless JSON contract exists), leaving only the browser/headless endpoints as the SPA contract. This avoids a competing form-based reset surface (see §11).

3. Proposed recovery architecture

The recovery flow delegates every security-sensitive primitive to allauth 65.21.0 / Django; the AgentGate project contributes only configuration, branding templates, and tests. No custom reset-token table, no custom crypto, no custom reset endpoints. 

React SPA                       Django backend (allauth 65.21.0 Headless @ /api/auth/headless/browser/v1)
│
│  GET  /config                      →  sets csrftoken cookie        (existing, AUTH-01)
│  POST /auth/password/request        {email}                        →  RequestPasswordResetView
│       ├─ known, verified user ─────→ send_mail("password_reset_key")  (reset link with key=uid-token)
│       └─ unknown email ────────────→ send_mail("unknown_account")     (enumeration-resistant)
│       ← always 200 (RequestPasswordResponse)        [rate-limited: 20/m/ip, 5/m/key(email hash)]
│
│  --- user clicks link in email → SPA route /reset-password/:key ---
│
│  POST /auth/password/reset         {key, password}              →  ResetPasswordView
│       ├─ key valid & not expired ─→ reset_password() + finalize_password_reset()
│       │                              (set_password → token now invalid by hash binding)
│       ├─ key invalid/expired ──────→ 400 {"errors":[...]}  ("invalid_password_reset")
│       │  ← always 200 AuthenticationResponse, is_authenticated=false (LOGIN_ON_PASSWORD_RESET=False)
│       → notification email "password_reset" sent
│         [rate-limited: 20/m/ip]
│
│  POST /account/password/change     {current_password, new_password}  →  ChangePasswordView (authed)
│       ├─ current_password valid    → set_password + update_session_auth_hash (session kept)
│       ├─ current_password invalid  → 400 {"errors":[...]}
│         [rate-limited: 5/m/user]  [CSRF required]

Do not reimplement

The contract must not introduce POST /accounts/password/reset/ (JSON) or any other custom recovery endpoint. The allauth Headless endpoints above are the single source of truth. Custom endpoints would duplicate allauth’s CSRF, rate-limiting, and enumeration logic and would silently bypass them. The only new code should be configuration + templates + tests.

Recovery never carries identity

None of the three endpoints create, read, update, or infer OrgMembership or role. The CustomAccountAdapter.clean_email (§1.3) explicitly does not auto-assign an organization on signup, and the password-reset/password-change flows touch only the password column of accounts_user. Recovery therefore cannot grant organization membership or elevated permissions by construction.

Framework-provided (inherit, do not reimplement): token statelessness & single-use binding, password hashing, AUTH_PASSWORD_VALIDATORS, enumeration-resistant reset-request response, built-in rate limits, CSRF middleware integration.

7. Session and CSRF behavior

7.1 CSRF bootstrap (unchanged by AUTH-02)

The browser-client flow (already AUTH-01) requires:

  1. GET /api/auth/headless/browser/v1/config — the allauth browser_view decorator calls get_token(request), which sets the csrftoken cookie (and an anonymous session). Returns config JSON.
  2. All subsequent POST/DELETE requests carry X-CSRFToken: <csrftoken cookie value> and credentials: "include". Without the header the browser client returns 403 (verified by test_login_without_csrf_token_is_rejected in AUTH-01).

Password recovery follows the same rule: the reset-request and reset-confirm POSTs must include the X-CSRFToken header obtained from GET /config. Reset endpoints are anonymous in spirit, but because the browser client issues a session cookie, Django’s CsrfViewMiddleware enforces CSRF on unsafe methods — omitting the header yields 403, exactly as the login/logout CSRF tests already demonstrate. This keeps agent-key (Bearer) and dashboard (session+CSRF) auth fully separated.

Recommended default for AgentGate

For password change, preserve the session (LOGOUT_ON_PASSWORD_CHANGE=False) so the SPA does not kick the user back to the login screen after rotating a password — but combine this with allauth.usersessions (USERSESSIONS_ENABLED=True) so that password change/reset terminates other live sessions, closing the session-hijack-survives-rotation gap in §5.1. This is a §11 decision because it adds a new allauth extras dependency.

8. React SPA integration contract

The current SessionProvider.tsx / context.ts hold only an agent key and a local request history; there is no dashboard-user/session state and no auth routes in App.tsx. Recovery integration therefore extends the session layer, not the agent API client (frontend/src/api/spendRequests.ts must remain untouched — agent-key path is independent).

8.1 Reset flow (SPA)

  1. Forgot-password screen (/forgot-password, unauthenticated route): call GET /api/auth/headless/browser/v1/config (bootstraps csrftoken), then POST .../auth/password/request with {email} and X-CSRFToken. Treat any 2xx as success and show a static “check your email” page (do not reveal whether the address is registered — see §5.1).
  2. Reset-confirm screen (/reset-password/:key, unauthenticated route): the key route param is the uidb36-token string from the email link. Call POST .../auth/password/reset with {key, new_password} and X-CSRFToken (single password field maps to the SPA’s two-field confirm UI — the client validates equality before sending).
  3. On 200: redirect to /login (reset does not auto-login). On 400: render {"errors":[...]} (expired/tampered/reused token → invalid_password_reset). On 429: show a retry-after / rate-limit notice.

8.2 Change-password flow (SPA, authenticated)

  1. Guarded behind an authenticated session; GET /api/auth/user/ must be 200 before showing the screen.
  2. POST .../account/password/change with {current_password, new_password} + X-CSRFToken.
  3. 200: optimistic UI (password updated; session preserved). 400: surface {"errors":[...]} — wrong current password, or new password failing validators.

9. Implementation plan for AUTH-02B

The current worktree (feat/account-recovery @ 2f9c3b6) does not yet contain allauth. AUTH-02B should first rebase onto integration/auth-crud (3d6fef9) so the allauth 65.21.0 foundation is present, then make the changes below. This AUTH-02A checkpoint introduces no code.

  1. Rebase onto the baseline. Reopen this worktree on integration/auth-crud (3d6fef9) so django-allauth==65.21.0, the headless URL includes, CustomAccountAdapter, and the auth tests are present. Shared-file risk: backend/config/settings/base.py and backend/config/urls.py.
  2. Set the token timeout. Add PASSWORD_RESET_TIMEOUT = 3600 to config/settings/base.py. This is a Django setting (correcting the non-existent ACCOUNT_PASSWORD_RESET_TIMEOUT cited in prior docs).
  3. Configure the SPA reset link. Set HEADLESS_FRONTEND_URLS = {"account_reset_password_from_key": "https://app.example/reset-password/{key}"} in base.py (origin from env). This makes allauth emit a SPA-routable link instead of a server-side /accounts/password/reset/key/... URL.
  4. Narrow the non-headless surface. Extend the existing _without_password_change filter in config/urls.py to also exclude the non-headless password/reset routes, so the only reset contract is the Headless JSON endpoints (no competing form surface).
  5. Brand the emails. Add override templates under backend/templates/account/email/ for password_reset_key, unknown_account, and password_reset, matching the project tone and the SPA link domain.
  6. Session policy. Decide LOGOUT_ON_PASSWORD_CHANGE and USERSESSIONS_ENABLED (see §5.1 / §11). Defaults recommended: keep LOGOUT_ON_PASSWORD_CHANGE=False (preserve session on change) and optionally enable allauth.usersessions to terminate other sessions on reset/change.
  7. E2E tests. Add backend/tests/test_auth_password_reset.py using the locmem email backend to assert: reset-request returns 200 for unknown & known emails; reset email is sent only to known verified users; code/link flow resets the password; reused/expired tokens return 400; password change requires current_password; rate limits (429) fire; GET /api/auth/user/ still 401 after reset.
