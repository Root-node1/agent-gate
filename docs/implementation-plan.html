Overview

This document breaks down the remaining work into 10 implementation phases. Each phase is internally sequential, but phases are designed to unblock specific parallel workstreams. Ownership is split between two developers with clear boundaries to avoid merge conflicts. Production deployment targets the existing Contaba VPS infrastructure.

Scope note: Authentication (including 2FA) and Gemini chatbot integration are documented as architectural requirements with task breakdowns (AUTH-01 through AUTH-06). Their implementation (code changes) is out of scope for this phase. See the individual architecture documents for spec details.

Phases

Phase 1 — Foundation (Backend API completeness)

Owner: Backend developer

Goal: Implement all missing backend endpoints identified in the API gap analysis.

  1. Create /v1/dashboard/spend-requests/ list endpoint with org-scope filtering
  2. Create /v1/dashboard/spend-requests/{id}/ detail endpoint
  3. Create /v1/dashboard/stats/ endpoint for dashboard charts
  4. Create /v1/dashboard/merchants/ endpoint for allow/block management
  5. Implement agent CRUD endpoints:
    • GET /v1/agents/ — list
    • POST /v1/agents/ — create
    • GET /v1/agents/{id}/ — detail
    • PATCH /v1/agents/{id}/ — suspend/reactivate
    • POST /v1/agents/{id}/rotate-key
    • POST /v1/agents/{id}/revoke-key
  6. Implement policy management:
    • POST /v1/policies/ — create new version
    • PATCH /v1/policies/{id}/ — update (new version)
    • POST /v1/policies/{id}/merchant-rules/
    • DELETE /v1/policies/{id}/merchant-rules/{rule_id}/
  7. Implement settings endpoints (workspace, team, PayPal)

Phase 2 — Authentication (Backend), AUTH-01 through AUTH-06

Owner: Backend developer

Goal: Implement email/password, GitHub OAuth, email verification, secure logout, password reset, 2FA (TOTP + recovery codes), and authentication rate limiting.

Authentication is broken into six independent, sequential tasks (AUTH-01 through AUTH-06). Each task has its own acceptance criteria and verification commands.

AUTH-01 — Email/password signup and login

Dependencies: None

  • Add django-allauth to requirements.txt
  • Configure allauth in settings/base.py with ACCOUNT_EMAIL_VERIFICATION
  • Implement /accounts/signup/ and /accounts/login/ endpoints
  • Create custom signup adapter restricting domains to allowlisted org domains

Acceptance criteria: Users can sign up with email + password; account is created but inactive until email verification; login works but redirects to verification page.

Verification: pytest tests/test_auth_signup_login.py

AUTH-02 — Email verification and secure logout

Dependencies: AUTH-01

  • Configure email templates (confirmation, password reset)
  • Implement /accounts/logout/ endpoint (clears session, CSRF token)
  • Wire EmailBackend to SMTP (Mailgun or local console in dev)

Acceptance criteria: Unverified users cannot log in; verified users can log out securely.

Verification: pytest tests/test_auth_verification_logout.py

AUTH-03 — Password reset and change

Dependencies: AUTH-02

  • Implement password reset with expiring, single-use links
  • Implement password change endpoint (requires current password)
  • Integrate allauth password reset adapter with rate-limited token generation

Acceptance criteria: Password reset links expire after 1 hour and can only be used once; password change requires current password.

Verification: pytest tests/test_auth_password.py

AUTH-04 — GitHub OAuth

Dependencies: AUTH-01

  • Register GitHub OAuth app
  • Configure SOCIALACCOUNT_PROVIDERS in settings
  • Implement SOCIALACCOUNT_LOGIN_BY_CODE_REQUIRED = True (for SPA flow)
  • Create custom social account adapter for org domain restriction

Acceptance criteria: Users can log in via GitHub; callback URL verified; social account linked to User model.

Verification: pytest tests/test_auth_github.py

AUTH-05 — TOTP two-factor authentication

Dependencies: AUTH-02

  • Add django-two-factor-auth or dj-totp to requirements.txt
  • Implement TOTP setup: generate secret, QR code, verify 6-digit code
  • Generate recovery codes (10 single-use backup codes)
  • Implement second-factor verification after both password and GitHub login
  • Enforce 2FA for administrators and payment approvers

Acceptance criteria: Users can enroll TOTP via QR code; 2FA required for admin/approver roles after primary login; 10 recovery codes generated (single-use); 2FA can be disabled only after re-verification.

Verification: pytest tests/test_auth_2fa.py

AUTH-06 — Organization-scoped RBAC and rate limiting

Dependencies: AUTH-05

  • Implement OrgMembership signal handler for auto-assignment on signup/login
  • Add IsDashboardUser, IsApprover, IsOrganizationAdmin permission classes
  • Add GET /api/auth/user/ session endpoint (returns user + orgs + roles)
  • Implement authentication rate limiting (Django Ratelimit or DRF throttles)
  • Configure django-axes or custom brute-force protection

Acceptance criteria: User is auto-assigned to organization based on email domain; permissions checked per request; brute-force login attempts are rate-limited (5 failures → 15-minute lockout).

Verification: pytest tests/test_auth_rbac.py && pytest tests/test_auth_rate_limit.py

See Authentication Architecture for the full design including 2FA, session management, CSRF protection, and RBAC details.

Phase 3 — Authentication (Frontend)

Owner: Frontend developer

Goal: Add login/logout/signup UI with 2FA support and provider redirect flow.

  1. Create /login page with email/password form and GitHub OAuth button
  2. Create /signup page with email verification flow
  3. Create /2fa/setup page with TOTP QR code scanner
  4. Create /2fa/verify page for second-factor entry after primary login
  5. Create /recovery-codes page to display and manage backup codes
  6. Create /password/reset and /password/change pages
  7. Replace SessionProvider implementation to use session cookie (not demo)
    • On mount: GET /api/auth/user/ to establish current user + orgs + roles + 2FA status
    • logout() calls /accounts/logout/
    • CSRF token handling via X-CSRFToken header
  8. Convert demo/store.ts calls to real API calls
  9. Guard all routes with auth (except /login, /signup)
  10. Add role-based UI (admin controls only visible to admins/approvers)
  11. Add Require2FA wrapper component for admin/approver routes

Phase 4 — Frontend-Backend Integration (Parity)

Owners: Frontend developer (primary), Backend developer (API fixes)

Goal: Replace all demo store calls with real API.

  1. Fix type mismatch: backend rule objects use code (string) + message (string), frontend expects code: object with rule_code. Update frontend types.
  2. Fix pagination mismatch: frontend uses page parameter, backend uses offset/limit. Update frontend to match backend.
  3. Fix audit response mismatch: backend returns string timestamps, frontend expects numbers. Update frontend or serializer.
  4. Implement spend request list/detail via real API
  5. Implement approval list/approve/deny via real API
  6. Implement dashboard stats via real API
  7. Implement merchant management via real API
  8. Implement agent management via real API (admin-only views)
  9. Implement policy management via real API (admin-only views)
Barrier to production: All 11/17 dashboard screens must use the real API, not the demo store. This is the single largest integration task.

Phase 5 — PayPal Integration

Owner: Backend developer

Goal: Implement PayPal payment execution on approved spend requests.

  1. Add PayPal SDK dependency (paypalcheckoutsdk or new REST SDK)
  2. Create apps/payments/services.py with execute_payment(spend_request)
  3. Implement PaymentService.execute_payment():
    • Generate PayPal order via API
    • Return approval URL (for agent-side approval flow)
    • Capture funds when approved
    • Handle PayPal webhooks for payment status updates
  4. Add PayPal webhook model and endpoint: POST /v1/payments/webhook/paypal/
  5. Link payment to spend request in audit log

Phase 6 — Gemini Chatbot Integration

Owner: Backend developer

Goal: Implement backend chatbot endpoint that proxies to Gemini.

  1. Add google-genai SDK to requirements.txt
  2. Create apps/chat/services.py with chat(message, conversation_id, user)
  3. Implement conversation model (apps/chat/models.py) with per-user scoping
  4. Implement POST /v1/chat/ endpoint (session-authenticated)
  5. System prompt with read-only guardrails (see Gemini architecture doc)
  6. Add per-user rate limiting (30 requests/minute)
  7. Add request/response logging to audit trail

See Gemini Chatbot Integration for the full design.

Phase 7 — Gemini Chatbot (Frontend)

Owner: Frontend developer

Goal: Create chat UI in the dashboard.

  1. Create /chat route with message-input + conversation panel
  2. Implement ChatClient in src/api/ calling /v1/chat/
  3. Add streaming support (Server-Sent Events or WebSocket) for real-time responses
  4. Display token usage in the UI
  5. Conversation history scoped to current user session

Phase 8 — Testing & Validation

Owners: Both developers

Goal: Comprehensive test coverage for new features.

  1. Backend: add tests for all new endpoints (authentication, agents, policies, chatbot, PayPal webhooks)
  2. Backend: integration tests for auth + permissions + org scoping
  3. Frontend: component tests for login/signup/chat UI
  4. Frontend: e2e tests for full spend-request-submission flow
  5. Security: run pip-audit + npm audit, fix vulnerabilities
  6. Security: run OWASP ZAP or similar against staging
  7. Audit: verify verify_audit command passes with new data

Phase 9 — Environment Configuration

Owners: Both developers (shared ops concern)

Goal: Align staging and production configuration.

  1. Update backend/.env.example with new variables (allauth, PayPal, Gemini, TOTP)
  2. Configure environment variables on the Contabo VPS:
    • DJANGO_ALLOWED_HOSTS (staging + production)
    • CSRF_TRUSTED_ORIGINS (staging + production)
    • DATABASE_URL (Neon staging branch + production)
    • TRUSTED_PROXY_COUNT=1 (Caddy fronting Gunicorn)
    • DJANGO_ADMIN_PATH (custom admin path in production)
    • PayPal sandbox credentials (staging) / live credentials (prod)
    • Gemini API key (staging + prod)
    • GitHub OAuth app ID/secret (staging + prod)
  3. Configure email delivery (Mailgun or SMTP) for staging and production
  4. Set DJANGO_SETTINGS_MODULE=config.settings.prod in Docker Compose env file
  5. Verify DATABASE_URL configuration: Neon pooled URL for web, direct URL for Procrastinate worker

Phase 10 — Final Validation & Go/No-Go

Owner: Both developers + coordinator review

Goal: Final checklist before production deployment.

  1. ✅ All CI checks pass (backend tests on PostgreSQL, frontend lint + build)
  2. ✅ Security audit clean (pip-audit, npm audit, OWASP ZAP)
  3. ✅ All dashboard screens use real API (demo store removed)
  4. ✅ Authentication working (email/password + GitHub OAuth + 2FA for admin/approver)
  5. ✅ PayPal integration tested against sandbox
  6. ✅ Gemini chatbot tested with guardrail prompts
  7. ✅ Audit log integrity verified (verify_audit passes)
  8. ✅ Staging environment deployed and smoke-tested
  9. ✅ Rollback plan documented
  10. ✅ Monitoring alerts configured

Go/No-Go Decision

This checklist gates production deployment. All criteria must pass.
