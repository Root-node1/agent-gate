## 2. Backup Strategy

### 2.1 Neon capabilities (to verify against account/plan)

The following Neon features are referenced in repository documentation and general Neon documentation. **Verify against the actual Neon plan and dashboard before relying on them:**

- **Point-in-time recovery (PITR):** Neon provides branching and restore points. Retention period depends on the plan (free tier: limited; paid: configurable). **Open item: confirm retention days.**
- **Branching:** Create a branch from any point in time (instant, copy-on-write). Useful for test restores without affecting production.
- **Automated backups:** Neon manages storage-level backups. Retention depends on plan. **Open item: confirm backup frequency and retention.**
- **Logical backups via `pg_dump`:** Always available via the direct connection URL. This is AgentGate's independent backup layer.

### 2.2 Independent logical backups (AgentGate-maintained)

Regardless of Neon's managed backups, AgentGate must maintain **independent** `pg_dump` backups stored off-server:

- **Frequency:** Daily (proposed; see RPO below).
- **Format:** Custom format (`--format=custom`) for selective restore.
- **Scope:** Full database dump (all tables including Procrastinate and audit).
- **Tool:** `pg_dump` from a PostgreSQL 17-compatible client.
- **Command:**
  ```bash
  pg_dump "$DATABASE_URL" --format=custom --file=agentgate-$(date +%F).dump
  ```
- **Direct URL required:** Use the direct Neon URL (not the transaction pooler) to ensure a consistent snapshot.

### 2.3 Dump integrity verification

1. **File size check:** Compare against previous dumps; alert on significant size drops.
2. **Restore test:** Restore into a temporary database and run Django checks (see §4).
3. **Audit chain:** Run `python manage.py verify_audit` against the restored database.
4. **Checksum:** Generate `sha256sum` of the dump file and store alongside it.

### 2.4 Encryption

- Encrypt dumps before off-server storage using `gpg` (symmetric or asymmetric) or `age`.
- Example:
  ```bash
  gpg --symmetric --cipher-algo AES256 agentgate-$(date +%F).dump
  ```
- Store the encryption key in a secrets manager, NOT alongside the backups.
- Never store unencrypted dumps off-server.

### 2.5 Access control

- Backup credentials (Neon connection URL) stored in a secrets manager or password vault.
- Backup storage (S3, off-server disk, etc.) with IAM policies restricting access to backup operators only.
- No backup credentials in the application repository or image.
- Rotate backup credentials periodically.

### 2.6 Retention (proposed)

| Backup type | Frequency | Retention | Storage |
|---|---|---|---|
| Neon managed (PITR) | Continuous | Plan-dependent | Neon |
| Logical dump (full) | Daily | 30 days | Off-server encrypted |
| Logical dump (weekly) | Weekly | 90 days | Off-server encrypted |
| Logical dump (monthly) | Monthly | 12 months | Off-server encrypted (cold storage) |

**Open item:** Confirm Neon plan retention. Adjust logical backup retention to complement (not duplicate) Neon's.

### 2.7 Monitoring and alerting

- **Backup job monitoring:** Alert if a daily dump is not created within the expected window.
- **Size monitoring:** Alert on significant size deviation from the 7-day average.
- **Integrity monitoring:** Alert if `verify_audit` fails on the latest restore test.
- **Storage monitoring:** Alert when backup storage approaches capacity.
- **Recommended tooling:** Cron + simple script with email/Slack notification, or a backup service (e.g., pgBackRest, WAL-G) for production scale.

## 3. Restore Strategy

### 3.1 Core principle

**Never overwrite an existing database during a test restore.** Always restore into a separate, temporary database.

### 3.2 Full database recovery procedure

1. **Provision a temporary database** (Neon branch or local PostgreSQL 17 instance).
   ```bash
   # Neon: create a branch from the latest restore point (dashboard)
   # Local: createdb agentgate_restore_test
   ```

2. **Restore the dump:**
   ```bash
   pg_restore --dbname="$RESTORE_URL" --clean --if-exists agentgate-YYYY-MM-DD.dump
   ```
   (Omit `--clean` for a fresh database.)

3. **Verify schema and migration state:**
   ```bash
   DJANGO_SETTINGS_MODULE=config.settings.prod DATABASE_URL="$RESTORE_URL" \
     python manage.py showmigrations
   DJANGO_SETTINGS_MODULE=config.settings.prod DATABASE_URL="$RESTORE_URL" \
     python manage.py migrate --check
   ```

4. **Verify important records (counts, not values):**
   ```sql
   SELECT count(*) FROM accounts_user;
   SELECT count(*) FROM accounts_organization;
   SELECT count(*) FROM spend_spendrequest;
   SELECT count(*) FROM audit_auditevent;
   SELECT count(*) FROM procrastinate_jobs;
   ```

5. **Verify audit-chain integrity:**
   ```bash
   DJANGO_SETTINGS_MODULE=config.settings.prod DATABASE_URL="$RESTORE_URL" \
     python manage.py verify_audit
   ```

6. **Verify authentication records (presence only, no secrets):**
   - Confirm `accounts_user` has expected rows.
   - Confirm `agents_apikey` has expected prefixes (do NOT print key hashes).
   - Confirm MFA-related fields are populated where expected.

7. **Verify Procrastinate tables:**
   ```sql
   SELECT count(*) FROM procrastinate_jobs;
   SELECT count(*) FROM procrastinate_workers;
   ```

8. **Run Django checks:**
   ```bash
   DJANGO_SETTINGS_MODULE=config.settings.prod DATABASE_URL="$RESTORE_URL" \
     REDIS_URL="redis://localhost:6379/0" MFA_ENCRYPTION_KEY="..." \
     python manage.py check --deploy
   ```

9. **Run relevant tests against the restored database:**
   ```bash
   TEST_DATABASE_URL="$RESTORE_URL" python manage.py test
   ```

10. **Switch connectivity only after approval:**
    - Update `DATABASE_URL` in `.env.production` to point to the restored database.
    - Restart web and worker containers.
    - Verify `/readyz` returns 200.
    - Monitor logs for errors.

### 3.3 Recovery scenarios

| Scenario | Procedure |
|---|---|
| **Full database recovery** | Restore from latest dump into a new database; verify; switch `DATABASE_URL`. |
| **Accidental record deletion** | Restore from dump into a temporary database; extract the deleted rows; re-insert into production (manual, with approval). Never bulk-overwrite. |
| **Uploaded files recovery** | N/A — no media uploads exist. Static files are reproducible. |
| **Compromised VPS** | 1. Rotate all secrets (DJANGO_SECRET_KEY, MFA_ENCRYPTION_KEY, DB credentials, Redis password). 2. Provision new VPS. 3. Restore DB from off-server backup. 4. Redeploy from Git (verified commit). 5. Revoke all API keys. 6. Audit `verify_audit` for tampering. |

## 4. Recovery Objectives (Proposed — Requires Tech Lead Approval)

| Metric | Proposed target | Rationale |
|---|---|---|
| **RPO (Recovery Point Objective)** | 24 hours | Daily backups; acceptable for early-stage. Could reduce to 1 hour with WAL archiving (Neon PITR). |
| **RTO (Recovery Time Objective)** | 4 hours | Includes provisioning, restore, verification, and DNS/switch. Could reduce with tested runbooks and automation. |

**Trade-offs:**
- Higher backup frequency (hourly) reduces RPO but increases storage cost and complexity.
- WAL archiving (Neon PITR) provides near-zero RPO but depends on plan entitlements.
- Lower RTO requires automated restore scripts and pre-provisioned standby infrastructure.
- For early production, daily backups + tested restore procedure is a pragmatic starting point.

## 5. Network Isolation Observation (AG-08)

**Current state:** Caddy, web, worker, and Redis all share a single `internal` Docker network. Redis is not published to the host, but Caddy (edge-facing) and Redis (backend) are on the same network segment.

**Status: IMPLEMENTED (AG-10).**
- **Edge network:** Caddy + web only.
- **Backend network:** web + worker + Redis (with outbound access to Neon).
- This limits blast radius if a container is compromised and prevents edge services from reaching Redis directly.

**Trade-off:** Slightly more complex compose configuration. Not a blocker for initial deployment.
