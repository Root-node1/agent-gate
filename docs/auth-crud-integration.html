3. Authentication and CRUD compatibility

The auth-foundation branch provides SessionAuthentication-based dashboard authentication via django-allauth Headless, while the backend-crud branch provides DashboardSessionAuthentication (a SessionAuthentication subclass that returns 401 instead of 403 for unauthenticated requests). Both are compatible because:

  • Shared models: apps.accounts.models.Organization and OrgMembership exist at the merge-base; IsOrganizationAdmin and IsDashboardUser permissions (auth-foundation) are imported by backend-crud views.
  • AgentKeyAuthentication: Already in base.py at the merge-base; the agent CRUD views use DashboardSessionAuthentication for dashboard access and AgentKeyAuthentication for API access via the default auth classes.
  • Email verification: ACCOUNT_EMAIL_VERIFICATION = "mandatory" blocks unverified users from dashboard endpoints.
  • CSRF: CSRF_COOKIE_HTTPONLY = False allows the frontend to read the CSRF token; CSRF_TRUSTED_ORIGINS is configured in dev/test settings.

Contract details verified

  • expected_version required in PATCH/POST JSON bodies for optimistic concurrency (missing → 400, stale → 409).
  • If-Match header required for merchant-rule DELETE (missing/invalid → 400, stale → 409).
  • Immutable policy snapshots: each mutation creates a new policy version with a new UUID; original rows are never updated or deleted.
  • Major-unit request / minor-unit response: money fields in request bodies use decimal strings (e.g. "100.00"); responses use integer minor units (e.g. 10000).
  • 401/403/404 responses: anonymous → 401, authenticated non-member → 403, foreign organization → 404 (to prevent resource enumeration).
  • Audit events: every mutation records a POLICY_CHANGED or AGENT_CREATED event with actor type, actor ID, and action-specific payload fields.
