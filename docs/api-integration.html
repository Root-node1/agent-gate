Overview

The AgentGate API is a Django REST Framework (DRF) application with two authentication schemes:

  • Agent API Key (Authorization: Bearer agk_...) for programmatic spend request submission.
  • Django Session (cookie-based) for dashboard user operations.

Interactive documentation is available at /api/docs/ (Swagger UI) and the OpenAPI schema at /api/schema/. A Postman collection is available at docs/postman/AgentGate.postman_collection.json.

Authentication and authorization

Two authentication schemes

Agent API Key
  • Header: Authorization: Bearer agk_...
  • Only the prefix (12 chars) is stored in the database; the full key is SHA-256 hashed.
  • Comparison uses hmac.compare_digest (constant-time).
  • Suspended agents and revoked keys are rejected.
  • Rate-limited at 60/min per key (configurable via THROTTLE_AGENT).
Dashboard Session
  • Uses Django's built-in SessionAuthentication.
  • Requires an authenticated session (login via /api-auth/login/ or /accounts/login/).
  • State-changing requests require a valid X-CSRFToken header.
  • All dashboard endpoints are class-based views (APIView) with explicit authentication_classes = [SessionAuthentication] and a permission class.

Agent API

Submit spend request

POST /v1/spend-requests/ — Agent API Key authentication.

Request

Headers:

Authorization: Bearer agk_YOUR_AGENT_KEY
Idempotency-Key: 7f2c9d1e-4a3b-4c5d-8e9f-0a1b2c3d4e5f
Content-Type: application/json

Body:

{
  "amount": "10.00",            // decimal string, major units, min 0.01
  "currency": "USD",            // ISO-4217 code
  "merchant": "acme.com",       // will be normalized
  "purpose": "API credits",     // optional, max 2000 chars
  "source": "trusted",          // trusted | untrusted | web_page | email | invoice | tool_output
  "source_ref": "",             // optional context
  "evidence_excerpt": "",       // optional, max 4096 chars
  "destination_type": "paypal_email", // paypal_email | paypal_id | phone | url
  "destination_value": "seller@example.com"
}

Response (HTTP 201 for every decision)

Important: The status code is always 201. Read the decision field:

{
  "id": "uuid",
  "amount": "10.00",
  "currency": "USD",
  "merchant": "acme.com",
  "purpose": "API credits",
  "source": "trusted",
  "risk_score": 0,
  "decision": "allow",          // allow | deny | needs_approval
  "status": "approved",         // forward-only lifecycle
  "reasons": [{"code": "R01_AGENT_ACTIVE", "message": "..."}],
  "matched_rules": ["R03_MERCHANT_BLOCK"],
  "paypal_reference": null,
  "created_at": "2026-10-27T12:00:00Z",
  "approval": null              // outcome string or null
}

Status code summary

CodeMeaning
201Request processed — read decision in body
400Missing/invalid Idempotency-Key or validation error
401Invalid agent key
409Agent has no policy, or key reused with different body
429Rate limited

Get spend request

GET /v1/spend-requests/{id}/ — returns one of the calling agent's own requests. Returns 404 if the ID does not belong to this agent.

Dashboard API

All dashboard endpoints require SessionAuthentication and a valid CSRF token on state-changing requests.

Approvals

GET /v1/approvals/
Query params: outcome (pending|approved|denied|expired|all, default: pending), limit (max 200, default 50), offset. Returns paginated list scoped to the caller's organizations.
GET /v1/approvals/{id}/
Returns approval detail with nested spend request.
POST /v1/approvals/{id}/approve/
Approves a pending request. Re-runs the current policy and budget as a recheck. Returns 409 if a hard rule now denies, or the payee destination fingerprint changed. Body: {"note": "Approved after review"}
POST /v1/approvals/{id}/deny/
Denies a pending request. Body: {"note": "Denied by human review"}. Idempotent.

Policies

GET /v1/policies/
Query params: agent (UUID), limit, offset. Returns policy versions with nested merchant_rules array. Note: shape mismatch with frontend demo/types.ts.
POST /v1/policies/
Planned — create new policy version.
PATCH /v1/policies/{id}/
Planned — update policy (creates new version).
POST /v1/policies/{id}/merchant-rules/
Planned — add merchant rule.
DELETE /v1/policies/{id}/merchant-rules/{rule_id}/
Planned — remove merchant rule.

Audit log

GET /v1/audit/
Query params: event_type (single), agent (UUID), spend_request (UUID), after (integer cursor), limit, offset. Missing in backend: actor filter, date-range filter. Frontend uses: page/offset, not cursor.
GET /v1/audit/verify/
Admin-only. Verifies audit hash chains for all organizations where the caller is admin. Returns 409 if any chain is broken (tamper-evident). Returns 200 with checked and organizations counts on success.

Error responses

All errors use DRF's consistent format:

// Field-level validation error
{
  "amount": ["Ensure this value is greater than 0."]
}

// Detail-level error
{
  "detail": "Authentication credentials were not provided."
}

// Conflict (idempotency, recheck failure)
{
  "detail": "This approval has expired.",
  "rules": ["R03_MERCHANT_BLOCK"]  // only on 409 recheck failure
}

Pagination

All list endpoints use DashboardPagination (backend/apps/common/pagination.py): limit/offset style with a maximum page size of 200.

{
  "count": 1250,
  "next": "http://localhost:8000/v1/approvals/?limit=50&offset=50",
  "previous": null,
  "results": [
    {
      "id": "uuid",
      "amount": "10.00",
      "currency": "USD",
      "decision": "needs_approval"
    }
  ]
}

Missing endpoints

The following endpoints are referenced by the frontend dashboard but not yet implemented on the backend:

  • GET /v1/dashboard/spend-requests/ — dashboard spend request list (needs org-scope filtering)
  • GET /v1/dashboard/spend-requests/{id}/ — dashboard spend request detail
  • GET /v1/dashboard/stats/ — spending summary for dashboard charts
  • GET /v1/dashboard/merchants/ — merchant list for allow/block management
