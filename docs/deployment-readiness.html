Overview

AgentGate targets two deployment environments: staging (for testing) and production (for live traffic). The backend runs on a Contabo VPS using Docker Compose with Gunicorn as the WSGI server, Caddy as the reverse proxy with automatic HTTPS, and PostgreSQL on Neon as the database. A separate Procrastinate worker handles background jobs. Continuous integration runs on GitHub Actions, with deployment via GitHub Actions or an operator on the Contabo host.

Historical note: This document previously referenced Fly.io and Render as deployment targets. Those references have been corrected to match the actual Contabo VPS infrastructure. See backend/OPERATIONS.md for the canonical operations guide.

Docker Compose

The production deployment uses Docker Compose to orchestrate the backend, worker, and Caddy. The docker-compose.yml file lives at the repository root.

Reference docker-compose.yml

services:
  caddy:
    image: caddy:2-alpine
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
      - staticfiles:/app/staticfiles
    depends_on:
      - web

  web:
    build:
      context: .
      dockerfile: backend/Dockerfile
    restart: unless-stopped
    env_file:
      - backend/.env.production
    volumes:
      - staticfiles:/app/staticfiles
    expose:
      - "8000"
    command: gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 4

  worker:
    build:
      context: .
      dockerfile: backend/Dockerfile
    restart: unless-stopped
    env_file:
      - backend/.env.production
    command: python manage.py procrastinate_worker
    volumes:
      - staticfiles:/app/staticfiles

  redis:
    image: redis:7-alpine
    restart: unless-stopped

volumes:
  caddy_data:
  caddy_config:
  staticfiles:

VPS deployment procedure

To deploy on a fresh Contabo VPS:

  1. Provision Ubuntu 24.04 LTS VPS on Contabo
  2. Install Docker and Docker Compose: 
    apt update && apt install -y docker.io docker-compose
systemctl enable docker && systemctl start docker
  3. Clone the repository: 
    git clone git@github.com:Root-node1/agent-gate.git
cd agent-gate
  4. Create backend/.env.production with production secrets (see environment variables below)
  5. Build and start services: 
    docker compose build
docker compose up -d
  6. Run migrations and collectstatic: 
    docker compose run --rm web python manage.py migrate --noinput
docker compose run --rm web python manage.py createcachetable
docker compose run --rm web python manage.py collectstatic --noinput
  7. Restart services: 
    docker compose up -d

Staging environment checklist

Staging mirrors production on a separate Contabo VPS or staging environment:

  • Repository cloned to staging Contabo host
  • backend/.env.staging created with staging values
  • DJANGO_SETTINGS_MODULE=config.settings.prod set
  • DJANGO_ALLOWED_HOSTS set to staging domain
  • CSRF_TRUSTED_ORIGINS includes staging frontend origin
  • SECURE_SSL_REDIRECT=True
  • DATABASE_URL set to Neon staging branch
  • Database migrations applied (python manage.py migrate --noinput)
  • Static files collected (python manage.py collectstatic --noinput)
  • Caddy serving HTTPS with Let's Encrypt
  • Gunicorn workers started (4 workers)
  • Procrastinate worker started
  • Health checks pass: /healthz, /readyz
  • Email delivery configured and tested
  • GitHub OAuth app configured with staging callback URL
  • PayPal sandbox credentials configured and tested
  • Gemini API key configured with quota

Staging smoke test

  1. Health check: GET /healthz returns 200
  2. Readiness: GET /readyz returns 200 with database connected
  3. Login: User can log in via email/password and GitHub OAuth
  4. Agent key: Valid agent can submit a spend request
  5. Demonate: A spend request triggers rules correctly
  6. Approval: Approver can approve/deny a request
  7. Audit: Audit log entries are written with hash chaining
  8. Chatbot: Authenticated user can send/receive chat messages

Production requirements

Important: Production secrets must NEVER be committed to the repository. Use environment files on the Contabo host, protected by filesystem permissions (600).

Security requirements

  • DJANGO_SECRET_KEY — random 50+ chars, never committed to git
  • DJANGO_ALLOWED_HOSTS — set to production domain(s)
  • CSRF_TRUSTED_ORIGINS — set to production frontend origin
  • DEBUG=False
  • HTTPS everywhere (TLS 1.2+, managed by Caddy/Let's Encrypt)
  • SESSION_COOKIE_SECURE=True, CSRF_COOKIE_SECURE=True
  • SECURE_HSTS_SECONDS=31536000
  • SECURE_CONTENT_TYPE_NOSNIFF=True
  • X_FRAME_OPTIONS=DENY (set in prod settings)
  • PayPal web webhook endpoint verified with signature check
  • API keys stored as hashes (SHA-256), never plaintext
  • All inputs validated at serializer level
  • Rate limiting active on all endpoints (60/min agent, 20/min anon)
  • /admin/ behind IP allowlist or not publicly routed

GitHub Actions

The CI pipeline (.github/workflows/ci.yml) has three jobs, plus a manual deployment workflow:

Database operations

Migrations

All migrations are applied via docker compose run --rm web python manage.py migrate. The migration check in CI (makemigrations --check --dry-run) prevents drift.

Encrypted off-server backups

Backups are performed using pg_dump with encryption, stored on off-server storage:

#!/bin/bash
# backup.sh — run daily via cron on Contabo VPS
# Requires: GPG key for encryption, off-server storage (S3 / Hetzner Storage Box)

set -euo pipefail

DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="agentgate_${DATE}.dump"
ENCRYPTED_FILE="${BACKUP_FILE}.gpg"

# Take a consistent snapshot
pg_dump "$DATABASE_URL" --format=custom --file="$BACKUP_FILE"

# Encrypt with GPG (recipient is ops team key)
gpg --encrypt --recipient ops@your-domain.com "$BACKUP_FILE"

# Upload to off-server storage
aws s3 cp "$ENCRYPTED_FILE" s3://agentgate-backups/

# Remove local copies
rm -f "$BACKUP_FILE" "$ENCRYPTED_FILE"

echo "Backup complete: $ENCRYPTED_FILE" | mail -s "Backup OK" ops@your-domain.com

Cron entry (daily at 2 AM):

0 2 * * * /opt/agent-gate/backup.sh

Restore procedure

To restore from an encrypted backup:

#!/bin/bash
# restore.sh — restore from backup

set -euo pipefail

BACKUP_FILE=$1  # e.g., agentgate_20261027_020000.dump.gpg

# Download from off-server storage
aws s3 cp "s3://agentgate-backups/$BACKUP_FILE" .

# Decrypt
gpg --decrypt "$BACKUP_FILE" > "agentgate_restore.dump"

# Restore (requires database downtime)
pg_restore "$DATABASE_URL" --clean --if-exists --no-owner "agentgate_restore.dump"

# Clean up
rm -f "$BACKUP_FILE" "agentgate_restore.dump"

Restore verification

After restoring, verify integrity:

  1. Run python manage.py verify_audit — audit chain must pass
  2. Spot-check spend request counts: SELECT COUNT(*) FROM apps_spend_spendrequest
  3. Verify approvals are intact: SELECT COUNT(*) FROM apps_approvals_approval
  4. Confirm agent API keys still work (submit test spend request)

Rollback procedures

Application rollback

Docker Compose rollback by reverting the container image:

# Stop current services
docker compose down

# Revert to previous commit
git reset --hard HEAD~1

# Rebuild and restart
docker compose build
docker compose up -d
Warning: Application rollbacks do not roll back database migrations. If the previous version is incompatible with the current database schema, you must also restore from backup. Always test migrations before deploying.

Database rollback

Django migrations are forward-only by default. For a destructive rollback:

  1. Identify the target migration: 
    docker compose run --rm web python manage.py showmigrations
  2. Roll back to the target migration: 
    docker compose run --rm web python manage.py migrate apps_spend 0005_previous_migration
  3. If rollback is not possible, restore from encrypted off-server backup (see above)

Logging

Backend logs (via Docker stdout): Gunicorn and Django logs are captured by Docker and can be forwarded to a log aggregator (e.g., Loki, Papertrail) via Docker logging driver:

# docker-compose.yml
services:
  web:
    # ...
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"

Log categories:

  • Access logs — request method, path, status, duration
  • Auth events — login, logout, failed attempts, 2FA verification
  • Spend requests — every decision (allow/deny/approve), matched rules
  • Audit events — appended to audit log table
  • Payment events — PayPal webhook events, status changes
  • Errors — unhandled exceptions with traceback

Audit verification script

Run the audit chain verification periodically (hourly via cron on Contabo host):

#!/bin/bash
# verify-audit.sh — hourly cron
set -e

docker compose run --rm web python manage.py verify_audit --all

if [ $? -ne 0 ]; then
  echo "ERROR: Audit chain verification failed" | \
    mail -s "Audit verification FAILED" ops@your-domain.com
  exit 1
fi

echo "Audit chain verified OK"

Cron entry (hourly):

0 * * * * /opt/agent-gate/verify-audit.sh
