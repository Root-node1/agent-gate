AgentKeyAuthentication reads Authorization: Bearer <key>, extracts the first 12 chars as the prefix, looks up the ApiKey row where revoked_at IS NULL and agent.status = 'active', then does a constant-time hash comparison. It updates last_used_at at most once per minute.

2. Proposed API request/response contracts

Agents

GET /v1/agents/

Auth: SessionAuthentication · Permission: IsDashboardUser

Query params:

limit
Integer, 1-200, default 50.
offset
Integer, default 0.

Response (200): paginated list of agents scoped to the caller's organizations. Returns only agents where the caller has at least one OrgMembership.

{
  "count": 3,
  "next": "http://localhost:8000/v1/agents/?limit=50&offset=50",
  "previous": null,
  "results": [
    {
      "id": "uuid",
      "name": "billing-agent",
      "status": "active",
      "created_at": "2026-10-27T12:00:00Z",
      "updated_at": "2026-10-27T12:00:00Z",
      "current_key_prefix": "agk_1a2b3c4d5e6f"
    }
  ]
}

Security note: current_key_prefix returns only the indexed prefix (12 chars). The full key hash is never exposed. If the agent has no non-revoked keys, the field is null.

POST /v1/agents/

Auth: SessionAuthentication · Permission: IsOrganizationAdmin

Creates an agent and its first API key in one atomic operation (reuses Agent.create_with_key).

Request body:

{
  "name": "billing-agent",
  "organization": "uuid"
}

Validation:

  • name: required, 1-100 characters, no leading/trailing whitespace.
  • organization: required, must be a valid UUID belonging to an org the caller administers.
  • Name uniqueness per organization is enforced by the unique_agent_name_per_org database constraint; duplicate submissions return 400.

Response (201):

{
  "id": "uuid",
  "name": "billing-agent",
  "organization": "uuid",
  "status": "active",
  "created_at": "2026-10-27T12:00:00Z",
  "updated_at": "2026-10-27T12:00:00Z",
  "api_key": "agk_1a2b3c4d5e6f..."
}

Display-once semantics: The api_key field in the response body contains the raw key string (e.g. agk_...). This is the only time the full key is ever returned. It is never stored in the database in plaintext — only the prefix and SHA-256 hash are persisted (backend/apps/agents/keys.py:11-13). The frontend must show the key once and never request it again.

GET /v1/agents/{id}/

Auth: SessionAuthentication · Permission: IsDashboardUser

Response (200):

{
  "id": "uuid",
  "name": "billing-agent",
  "organization": "uuid",
  "organization_name": "Acme Corp",
  "status": "active",
  "created_at": "2026-10-27T12:00:00Z",
  "updated_at": "2026-10-27T12:00:00Z",

    "created_at": "2026-10-27T12:00:00Z",
    "last_used_at": "2026-10-27T12:00:01Z"
  },

    {
      "id": "uuid",
      "version": 1,
      "name": "Default policy",
      "currency": "USD"
    }
  ],
  "recent_spend_requests": 12,
  "today_spend_minor": 2500,
  "currency": "USD"
}

Security note: current_key returns only the prefix, creation timestamp, and last-used timestamp. key_hash and revoked_at are never exposed over the API. Returns 404 if the agent is outside the caller's organizations.

PATCH /v1/agents/{id}/

Auth: SessionAuthentication · Permission: IsOrganizationAdmin

Update agent fields. Primary use: suspend/reactivate.

Request body (partial update):

{
  "name": "billing-agent-renamed",
  "status": "suspended"
}

Validation:

  • status accepts only active or suspended.
  • Rename is permitted but must not collide with another active agent in the same organization.
  • If status changes from active to suspended, the agent's key is effectively invalidated (the authentication layer already rejects suspended agents — authentication.py:40).
  • If status changes to active, no key is regenerated automatically; the existing key continues to work.

Response (200): same shape as GET /v1/agents/{id}/.

Audit logging: PATCH must record an AuditEvent with event_type indicating the change. The existing AuditEvent.EventType enum (backend/apps/audit/models.py:27-31) does not yet have an AGENT_UPDATED type. A new event type is recommended (see #migrations). Alternatively, the existing agent auth events (agent.created, key.created, key.revoked) are logged by the management commands; the CRUD views should add agent.updated and agent.suspended.

POST /v1/agents/{id}/rotate-key

Auth: SessionAuthentication · Permission: IsOrganizationAdmin

Creates a new API key for the agent and revokes the previous key. The raw key is returned once.

Response (200):

{
  "id": "uuid",
  "name": "billing-agent",
  "status": "active",
  "current_key": {
    "prefix": "agk_9f8e7d6c5b4a",
    "created_at": "2026-10-27T12:00:00Z",
    "last_used_at": null
  },
  "api_key": "agk_9f8e7d6c5b4a..."
}

Behavior:

  • Creates a new ApiKey row via ApiKey.create_key(agent).
  • Sets revoked_at=now on the previous non-revoked key.
  • Both operations in a single @transaction.atomic block.
  • Records key.revoked audit event for the old key and key.created for the new key.

POST /v1/agents/{id}/revoke-key

Auth: SessionAuthentication · Permission: IsOrganizationAdmin

Revokes the agent's current non-revoked API key. The key is soft-deleted (marked via revoked_at); it is never purged from the database.

Request body: empty.

Response (200):

{
  "id": "uuid",
  "name": "billing-agent",
  "status": "active",
  "current_key": null,
  "revoked_key": {
    "prefix": "agk_1a2b3c4d5e6f",
    "revoked_at": "2026-10-27T12:00:00Z"
  }
}

After revocation, the key prefix is still returned for identification but the full key is permanently inaccessible. The agent's key prefix in list/detail responses becomes null. If the agent has no key at all, the endpoint returns 400 with {"detail": "No active API key to revoke."}.

Validation (mirrors create_agent management command, backend/apps/agents/management/commands/create_agent.py:54-70):

GET /v1/policies/{id}/

Auth: SessionAuthentication · Permission: IsDashboardUser

Returns the single policy version with its nested merchant_rules. Returns 404 if the policy's organization is outside the caller's memberships.

Response (200): same shape as a single entry in PolicySerializer.

PATCH /v1/policies/{id}/

Auth: SessionAuthentication · Permission: IsOrganizationAdmin

Creates a new policy version. Does NOT mutate the existing row. A new Policy is inserted with version = old.version + 1, copying all fields from the latest version of the same agent and applying the patch. All MerchantRule rows are recreated on the new policy version.

Request body (partial):

{
  "daily_budget_minor": 75000,
  "approval_threshold_minor": 2500,
  "merchant_rules": [
    {"merchant_ref": "newvendor.com", "kind": "allow"},
    {"merchant_ref": "evil.com", "kind": "block"}
  ]
}

Policy versioning is immutable: The existing Policy row is never updated in-place. A new row with an incremented version is created (backend/apps/policies/models.py:16-17 states "Editing a policy inserts a new row"). The unique constraint unique_policy_version_per_agent guarantees version ordering. The agent's latest version (highest version) is used for evaluation (backend/apps/spend/services.py:51).

Response (200): the new PolicySerializer representation.

POST /v1/policies/{id}/merchant-rules/

Auth: SessionAuthentication · Permission: IsOrganizationAdmin

Adds a single merchant rule to the latest policy version for an agent. This is a convenience endpoint; PATCH can also update the full set.

Request body:

{
  "merchant_ref": "newvendor.com",
  "kind": "allow",
  "note": "Primary vendor"
}

Response (201): the new MerchantRuleSerializer representation.

DELETE /v1/policies/{id}/merchant-rules/{rule_id}/

Auth: SessionAuthentication · Permission: IsOrganizationAdmin

Removes a merchant rule from the policy. Soft deletion is not used; the rule row is deleted. The policy version is preserved (only the rule is removed, not the policy). Returns 204 No Content.

4. API key lifecycle

Agent API keys are the only machine credentials in the system. Their lifecycle is:

Generation

  1. keys.py:new_raw_key() generates agk_ + 32 bytes of secrets.token_urlsafe(32).
  2. keys.py:hash_key() computes SHA-256 hex of the full raw key.
  3. keys.py:key_prefix() extracts the first 12 characters for DB lookup.
  4. The ApiKey row stores prefix (indexed, unique) and key_hash (not the raw key).

Display (once)

The raw key is returned ONLY at creation time:

  • On agent creation via Agent.create_with_key() (used by management commands).
  • On key rotation via the proposed POST /v1/agents/{id}/rotate-key endpoint.
After the API response, the raw key is irretrievable. If a user loses it, they must rotate.

Authentication

  1. Client sends Authorization: Bearer agk_....
  2. AgentKeyAuthentication.authenticate() (authentication.py:27-46) extracts the first 12 chars.
  3. Queries ApiKey.objects.select_related("agent").get(prefix=..., revoked_at__isnull=True, agent__status="active").
  4. If no match, raises AuthenticationFailed("Invalid or inactive agent key.") (401).
  5. If match found, calls hash_matches() — constant-time hmac.compare_digest comparison (keys.py:26-28).
  6. If hash does not match, raises AuthenticationFailed (401).
  7. Updates last_used_at at most once per minute (authentication.py:48-51).

Rotation

  1. POST /v1/agents/{id}/rotate-key creates a new ApiKey row.
  2. The previous non-revoked key gets revoked_at=now set before the new key is created (within the same transaction).
  3. Old key immediately stops working (excluded by revoked_at__isnull=True filter).
  4. New key returned once in the response body.
  5. Audit events: key.revoked for the old key, key.created for the new key.

Revocation (standalone)

  1. POST /v1/agents/{id}/revoke-key sets revoked_at=now on the current non-revoked key.
  2. The old key immediately stops working.
  3. No new key is created — the agent has zero active keys after this.
  4. To restore API access, the caller must rotate (which creates a new key).
  5. Audit event: key.revoked.

Suspension

  1. PATCH /v1/agents/{id}/ with status: "suspended" sets agent.status = "suspended".
  2. The authentication layer filters on agent__status="active", so all keys stop working immediately.
  3. No keys are revoked or rotated — the suspended status blocks authentication at the select_for_update query level.
  4. Reactivating restores authentication.

Security guarantees:

  • key_hash (SHA-256) is never returned in any API response or logged (agents/admin.py:30 makes it read-only in Django admin).
  • key_hash is never logged anywhere in the codebase.
  • No plaintext key is stored in any database column.
  • Revocation is a soft delete (revoked_at); rows are preserved for audit integrity.

5. Organization isolation requirements

Organization is the tenancy boundary. All dashboard endpoints must scope queries by organization__memberships__user=request.user. This pattern is used consistently in existing views (approvals/views.py:17, policies/views.py:23, audit/views.py:18).

Agent isolation

  • List agents return only those whose organization is in the caller's memberships.
  • Create agents: the organization field must reference an org the caller administers. The API must reject attempts to create agents in foreign organizations.
  • Detail/update/rotate/revoke: fetch the agent, then verify the caller has at least a viewer membership; admin permission required for writes.

Policy isolation

  • Policies are always linked to both organization and agent. Queries must filter on organization__memberships__user.
  • Creating a policy requires the specified agent's organization to be administered by the caller.
  • PATCH (new version) creates a policy row on the same agent; the agent's org isolation applies transitively.

Spend request isolation

  • Dashboard list returns all spend requests from all orgs the user belongs to.
  • Dashboard detail returns 404 if the spend request's organization is outside the user's memberships (not 403, to prevent enumeration).
  • No cross-org access is possible because the queryset filter is applied at the database level.

6. Model or migration changes required

After inspection of all model definitions and migrations, the following changes are recommended. None are strictly required to implement the contract; all are listed for completeness. No migrations are generated in this task.

Recommended: new audit event types

The existing AuditEvent.EventType enum (backend/apps/audit/models.py:17-31) includes agent.created, key.created, key.revoked, and policy.changed, but lacks an agent.updated type for suspension/reactivation and rename. This would be a CharField addition to the existing event_type choices:

AGENT_UPDATED = "agent.updated", "Agent updated"
AGENT_SUSPENDED = "agent.suspended", "Agent suspended"
AGENT_ACTIVATED = "agent.activated", "Agent activated"

This requires a migration in apps/audit/migrations/.

Recommended: key rotation helper

The ApiKey model has create_key() but no rotate() or revoke() method. A new method on the model or a service function would centralize the rotation+revoke transaction:

@classmethod
@transaction.atomic
def rotate_key(cls, agent):
    """Revoke the current key and create a replacement. Returns (new_key, raw_key)."""
    current = cls.objects.filter(agent=agent, revoked_at__isnull=True).first()
    if current:
        current.revoke()
    new_key, raw_key = cls.create_key(agent)
    return new_key, raw_key

def revoke(self):
    self.revoked_at = timezone.now()
    self.save(update_fields=["revoked_at", "updated_at"])

This does not require a migration; it is a model method addition.

Assessment: no schema-breaking changes needed

  • All fields needed for agent CRUD (Agent.name, Agent.status, Organization) already exist.
  • All fields needed for policy CRUD (Policy fields, MerchantRule) already exist.
  • All fields needed for dashboard spend request listing (SpendRequest fields) already exist; only a new serializer is needed for dashboard output.
  • The ApiKey model already tracks revoked_at for revocation semantics.

 Add new event types — audit integrity requires semantic precision; reusing agent.created for a rename would be misleading.
