3.2 Headless SPA flow (two modes)

allauth 65.21.0 Headless supports two social-login modes for the SPA:

Mode A: Server-side redirect (primary, recommended)
The SPA calls POST /api/auth/headless/browser/v1/auth/provider/redirect to trigger a server-side redirect to GitHub. The browser follows the redirect to GitHub’s consent page. GitHub then redirects back to the allauth callback (/accounts/github/login/callback/), which exchanges the code, creates/updates the social account, and redirects the browser back to the SPA’s callback_url with the session cookie set.
Mode B: Client-side token exchange (alternate)
The SPA opens GitHub’s authorize URL in a popup, captures the returned code, and POSTs it to POST /api/auth/headless/browser/v1/auth/provider/token. allauth exchanges the code server-side and returns an AuthenticationResponse. This mode is not needed for a same-origin dashboard and adds complexity (popup postMessage, token relay); it is documented for completeness only.

Mode A is the primary flow for AgentGate: the SPA is same-origin behind the same Django backend, so server-side redirect + cookie-based session works seamlessly with SameSite=Lax cookies.

5. Email verification behavior (critical)

5.1 GitHub’s email verification semantics

GitHub does verify email addresses. Every GitHub account must have at least one verified email. The GitHub API (GET /user/emails) returns each email with a verified boolean. However, the GET /user profile endpoint returns email as a string (which may be null if the user has set their email to private) and does not include a verified flag on the profile.

GitHub endpointEmail fieldverified flagallauth uses it?
GET /userdata["email"] (may be null for private emails)N/AYes — via extract_common_fields
GET /user/emailsemails[].email with emails[].verifiedPresentYes — via extract_email_addresses (allauth github/provider.py:46)

§5.1 confirmed: GitHub's native verified flag is preserved by default

Direct inspection of allauth 65.21.0 source confirms that GitHub’s per-email verified flag is trusted without any extra configuration, via two complementary mechanisms:

  1. extract_email_addresses (provider level): The GitHub provider’s extract_email_addresses (allauth/socialaccount/providers/github/provider.py:46) sets EmailAddress.verified = email["verified"] from GitHub’s /user/emails API. This works only if QUERY_EMAIL=True (i.e., SCOPE includes user:email), because GitHubOAuth2Adapter.complete_login (allauth/socialaccount/providers/github/views.py:38) only fetches /user/emails when app_settings.QUERY_EMAIL is True. Since ACCOUNT_SIGNUP_FIELDS includes "email*" (base.py:202), QUERY_EMAIL defaults to True, so user:email scope is included by default.
  2. cleanup_email_addresses (base provider): After extraction, the base provider’s cleanup_email_addresses method (allauth/socialaccount/providers/base/provider.py:194-226) runs:
    • Lines 219–220: it calls adapter.is_email_verified(self, address.email) for each address. If it returns True, it sets address.verified = True.
    • Crucially: it never sets address.verified = False. The adapter method can only upgrade verification, never downgrade it.
    Therefore, when extract_email_addresses sets verified=True from GitHub’s API response, cleanup_email_addresses preserves it, even though DefaultSocialAccountAdapter.is_email_verified() returns False by default (allauth/socialaccount/adapter.py:353-377).

§5.1 Tech Lead decision: Q2 resolved — no unconditional override

Per the Tech Lead’s decision, AgentGate will trust only email addresses explicitly verified by GitHub — i.e., rely on GitHub’s native per-email verified flag from the /user/emails API, which allauth correctly extracts and preserves by default. Do not set SOCIALACCOUNT_PROVIDERS["github"]["VERIFIED_EMAIL"] = True, as that would force-verify all emails from the GitHub provider (a broader trust than GitHub’s per-email API). A CustomSocialAccountAdapter.is_email_verified() override that returns True unconditionally for GitHub is also not recommended — it is functionally equivalent to VERIFIED_EMAIL=True (both can only upgrade, never downgrade) and bypasses the per-email granularity that the default behavior preserves.

5.3 Email verification policy (Tech Lead-approved)

Decision (Q2, APPROVED): Rely on GitHub’s native per-email verified flag. Do not set SOCIALACCOUNT_PROVIDERS["github"]["VERIFIED_EMAIL"] = True and do not override is_email_verified() to return True unconditionally for GitHub.

The precise mechanism (confirmed from allauth 65.21.0 source, allauth/socialaccount/providers/base/provider.py:219-220): 

# allauth/socialaccount/providers/base/provider.py:216-220
# Force verified emails
adapter = get_adapter()
for address in addresses:
    if adapter.is_email_verified(self, address.email):
        address.verified = True
# NOTE: there is NO "else: address.verified = False" line.
# The verified flag set by extract_email_addresses() is preserved.

This means:

  • GitHub emails marked verified: true by GitHub’s /user/emails API are stored as verified=True on the EmailAddress record — no additional configuration required.
  • GitHub emails marked verified: false are stored as verified=False. With ACCOUNT_EMAIL_VERIFICATION="mandatory" (already set at base.py:203), the EmailVerificationStage (allauth/account/stages.py) will send a verification code email and hold the login until the code is entered.
  • Since GitHub verifies all emails added to an account via SMTP before they become verified, in practice GitHub users will almost always have verified: true on their primary email. The verification-code fallback is a correct security default for edge cases (e.g., a newly-added unverified email).

If a CustomSocialAccountAdapter is still desired for future providers, it should inspect the SocialLogin.email_addresses list (which contains the per-email verified flags) rather than returning a blanket True: 

# backend/apps/accounts/adapters.py (EXTEND existing CustomAccountAdapter)

# Only add if a CustomSocialAccountAdapter is needed for other providers.
# For GitHub-only, the default is_email_verified() behavior is correct.

from allauth.socialaccount.adapter import DefaultSocialAccountAdapter

class CustomSocialAccountAdapter(DefaultSocialAccountAdapter):
    def is_email_verified(self, request, provider, email):
        # Trust GitHub's per-email verified flag from /user/emails
        # Do NOT force verify. Only this provider is trusted, and only for
        # emails GitHub itself marks as verified.
        if provider.id == "github":
            sociallogin = getattr(request, "_sociallogin", None)
            if sociallogin is not None:
                for addr in sociallogin.email_addresses:
                    if addr.email == email:
                        return addr.verified  # From GitHub API /user/emails
            # Fallback: if not in the extracted addresses, do not trust
            return False
        return super().is_email_verified(request, provider, email)

This fallback adapter is safe but redundant for the GitHub-only MVP: the default DefaultSocialAccountAdapter.is_email_verified() returns False, and cleanup_email_addresses preserves the verified=True already set by extract_email_addresses. The adapter would only add value if a future provider does not set verified per-email in extract_email_addresses.

6. Account linking and duplicate-email handling

6.1 Lookup logic (confirmed from allauth 65.21.0 source)

When GitHub redirects back to the callback, SocialLogin.lookup() (allauth/socialaccount/models.py:334) runs two lookups:

  1. _lookup_by_socialaccount: Searches SocialAccount.objects.get(provider="github", uid=<github_id>). If found, the existing social account is attached to the existing user. This is the primary lookup — it matches by GitHub’s unique user ID, not by email.
  2. _lookup_by_email: Only runs if _lookup_by_socialaccount fails AND SOCIALACCOUNT_EMAIL_AUTHENTICATION is enabled. Searches for a local user with a matching verified email address. If found, the social account is connected to that user but the password is wiped (allauth/socialaccount/internal/flows/email_authentication.py). This is disabled by default (SOCIALACCOUNT_EMAIL_AUTHENTICATION = False).

6.2 Duplicate-email policy

The project must not enable SOCIALACCOUNT_EMAIL_AUTHENTICATION (EMAIL_AUTHENTICATION in SOCIALACCOUNT_PROVIDERS). Rationale:

  • EMAIL_AUTHENTICATION=True causes allauth to silently log in an existing local user when a social login presents an email that matches that user’s verified email. This is an account-takeover vector if the social provider’s email verification is not fully trustworthy.
  • For a GitHub-only integration, GitHub’s email verification is reliable enough, but the project policy (per adapters.py:16) explicitly states that signup should never grant organization membership. Allowing email-based auto-linking would let an attacker connect their GitHub account to any existing AgentGate user.

Duplicate-email handling flow

If a user signs up via email/password with jane@example.com, then attempts GitHub login with a GitHub account whose primary email is also jane@example.com:

  1. _lookup_by_socialaccount fails (no existing GitHub SocialAccount for this user).
  2. _lookup_by_email is skipped (EMAIL_AUTHENTICATION=False).
  3. process_auto_signup_email checks assess_unique_email(email) (allauth/account/internal/flows/signup.py): the email already exists in EmailAddress → returns False (duplicate).
  4. Auto-signup is disabled. redirect_to_signup stashes the SocialLogin in the session and redirects to /accounts/signup/ (the socialaccount signup form).
  5. In the headless SPA flow, this surfaces as the provider_signup flow (allauth/headless/socialaccount/views.py:ProviderSignupView). The SPA receives a 401 with flows: [{id: "provider_signup", is_pending: true}].
  6. The user must manually connect their GitHub account by navigating to a future account-connections UI (GET/DELETE /api/auth/headless/browser/v1/account/ — ManageProvidersView). For AUTH-04A, this is out of scope. The SPA should display a message: "An account with this email already exists. Sign in with your password, then connect your GitHub account in settings."

6.3 New-user (first) flow

For a first-time GitHub user:

  1. _lookup_by_socialaccount fails (no existing SocialAccount).
  2. _lookup_by_email is skipped.
  3. process_auto_signup_email: the email is unique → assess_unique_email returns True.
  4. process_auto_signup returns True (email is unique, no phone required).
  5. save_user creates the User (with set_unusable_password()), then calls sociallogin.save() which creates the SocialAccount record and calls setup_user_email to create the EmailAddress record(s).
  6. complete_social_signup → complete_signup → perform_login → LoginStageController runs the login pipeline.
  7. If EMAIL_VERIFICATION=mandatory and the email is not verified → EmailVerificationStage sends a verification code, stashes the login, and the SPA receives a 401 with verify_email pending.
  8. If the email is verified → login completes, session is set, SPA receives 200.

7. CSRF, OAuth state, and session protections

7.1 OAuth state nonce (server-side, in session)

allauth 65.21.0 does not use PKCE by default (OAuth2Adapter has supports_state = True on the adapter, pkce_enabled_default = False on OAuth2Provider). Instead, it uses a session-stashed state nonce:

  • On redirect: Provider.stash_redirect_state() (allauth/socialaccount/providers/base/provider.py:245) saves a random 16-character state ID in request.session["socialaccount_states"] with a 10-minute TTL (STATE_TTL = 600 in allauth/socialaccount/internal/statekit.py:21).
  • The state ID is passed to GitHub as the state query parameter.
  • On callback: OAuth2CallbackView._get_state() (allauth/socialaccount/providers/oauth2/views.py:~170) unstashes the state from the session and verifies the state parameter matches. If mismatch or expired, render_authentication_error is called.
  • Maximum 10 stashed states per session (MAX_STATES = 10); oldest is GC’d.

8. User cancellation and provider failure handling

8.1 User cancels OAuth consent on GitHub

When the user clicks “Cancel” on GitHub’s consent screen (or denies the app), GitHub returns to the callback URL with error=access_denied. The OAuth2CallbackView.dispatch (allauth/socialaccount/providers/oauth2/views.py:~130) detects this and calls render_authentication_error with AuthError.CANCELLED.

In the headless flow, render_authentication_error calls on_authentication_error on the adapter (allauth/socialaccount/adapter.py:115), which by default is a no-op. Then, since HEADLESS_ENABLED is True, it delegates to allauth.headless.socialaccount.internal.on_authentication_error (allauth/headless/socialaccount/internal.py:~20), which redirects to the callback_url (the SPA’s next_url) with ?error=cancelled&error_process=login appended as query parameters.

The SPA must handle the redirect from the callback URL and inspect the error query parameter. On error=cancelled, display: “GitHub login was cancelled. Please try again.”

9. Separation: human sessions vs agent API keys

This is the most critical invariant. Agent API keys must never authenticate against dashboard or social-auth endpoints. Confirmed from the existing architecture:

Do not mix agent and user auth on any endpoint

The allauth headless and socialaccount endpoints exclusively use session cookies. They must never be added to any AgentKeyAuthentication-protected URL group. Agent keys authenticate as AgentPrincipal (an Organization + Agent context), not as a User — there is no User record to attach a social login to.

10. Organization membership and RBAC invariants

10.1 RBAC after GitHub login

When a new User is created via GitHub OAuth, the user has no OrgMembership record. The existing RBAC (IsDashboardUser) requires at least one membership, so a freshly-registered GitHub user cannot immediately access any dashboard endpoint:

10.3 Post-login user state

After a successful first-time GitHub login (email verified, allowed domain, no existing account):

  • User.is_active = True, user.password has an unusable hash (! prefix) — the user cannot use password login until they set one.
  • SocialAccount record exists (provider="github", uid=).
  • EmailConfirmation is skipped (GitHub email is trusted). No email sent.
  • No OrgMembership is created.
  • GET /api/auth/user/ returns 200 with is_email_verified=True but memberships=[].
  • SPA must redirect the user to an invite/accept flow to be added to an organization.

12. Frontend handoff requirements

The SPA (React/TypeScript, apps/web/src/) must implement the following sequence to initiate GitHub login:

  1. Bootstrap CSRF. Call GET /api/auth/headless/browser/v1/config on app load. The session cookie set here carries the csrftoken that all subsequent POSTs need in the X-CSRFToken header.
  2. Detect provider availability. Inspect the response for data.socialaccount.providers. If github is listed, show the "Sign in with GitHub" button.
  3. Initiate redirect. On click, POST /api/auth/headless/browser/v1/auth/provider/redirect with body {"provider": "github", "callback_url": "https://app.example.com/dashboard", "process": "login"} and header X-CSRFToken: <csrftoken>. The response is a 302 redirect to GitHub’s consent page. The browser follows it automatically (do not use fetch — use window.location.href = response.url since the 302 is to a cross-origin page).
  4. User consents on GitHub. GitHub redirects back to /accounts/github/login/callback/ with code and state.
  5. allauth processes. The backend exchanges the code, creates the user/social account, and 302-redirects the browser to the callback_url (the SPA’s /dashboard). Session and CSRF cookies are set.
  6. Resolve auth state. The SPA should call GET /api/auth/user/ on the /dashboard route to determine if the user is fully authenticated or if a verification stage is pending.

CSRF header name

The allauth headless flow uses Django’s default csrftoken cookie name. The SPA must read it from document.cookie and send it as the X-CSRFToken header on all state-changing POSTs. This is already the existing contract used by POST /auth/login and POST /auth/signup.

Items explicitly out of scope for this checkpoint

  • Account-connection UI (listing connected social accounts on the dashboard): allauth.headless.socialaccount.views.ManageProvidersView already provides the API, but the SPA page itself is a future deliverable.
  • GitHub App (vs OAuth App) integration: GitHub Apps use a different authorization flow (App’s installations endpoint). This is NOT needed for the dashboard login flow.
  • Email-based account linking: Allowing users to connect their GitHub account to an existing email/password account requires a future account-connections feature.
