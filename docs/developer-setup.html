Overview

AgentGate is a spending firewall between AI agents and PayPal. The agent asks, AgentGate decides: allow, deny, or needs human approval. Budgets, merchant rules, and approval thresholds are enforced in code, and every decision is written to an append-only, hash-chained audit log.

This page documents the developer setup.

Quick start

The simplest way to get both servers running locally:

git clone git@github.com:Root-node1/agent-gate.git
cd agent-gate
./run.sh

run.sh creates the Python venv, installs dependencies, generates .env, applies migrations, and starts both servers:

  • Backend: http://localhost:8000
  • Frontend: http://localhost:5173

Stop both with Ctrl+C.

API authentication

Agent API (programmatic)

Agents authenticate with a Bearer token:

Authorization: Bearer agk_...
  • Key prefix is agk_ followed by 43 URL-safe characters.
  • Only the prefix (12 chars) is stored indexed; the full key is SHA-256 hashed.
  • Comparison is constant-time (hmac.compare_digest).
  • Suspended agents and revoked keys are rejected.
  • Rate limit: 60/min per key (configurable via THROTTLE_AGENT).

Dashboard auth (session)

Dashboard users authenticate via Django sessions:

POST /api-auth/login/   # sets session cookie
POST /api-auth/logout/  # clears session cookie

Role-based permissions (checked against OrgMembership):

PermissionRoles
IsDashboardUseradmin, approver, viewer
IsApproveradmin, approver
IsOrganizationAdminadmin only

Planned: Email/password signup and GitHub OAuth login via django-allauth. See Authentication Architecture for details.

Rule engine

The engine (backend/engine/) is a pure Python package with no Django imports (enforced by .importlinter). Call engine.evaluate() with normalized inputs.

Rule codes

CodeNameTypeDescription
R01AGENT_ACTIVEDenyAgent is not active
R02CURRENCYDenyCurrency mismatch
R03MERCHANT_BLOCKDenyMerchant on block list
R04MERCHANT_ALLOWDenyAllow list exists, merchant not on it
R05PER_TX_CAPDenyAmount ≤0 or > cap
R06DAILY_BUDGETDenyExceeds daily budget
R07MONTHLY_BUDGETDenyExceeds monthly budget
R08VELOCITYApprovalRecent request count ≥ max
R09MERCHANT_WINDOWApprovalRecent merchant spend > cap
R10APPROVAL_THRESHOLDApprovalAmount ≥ threshold
R13UNTRUSTED_SOURCEApproval/DenySource ≠ trusted (configurable)
R14INJECTION_PATTERNDenyDeterministic phrase match
R16WEEKLY_BUDGETDenyExceeds weekly budget

Precedence: Any deny → deny; else any approval reason → needs_approval; else allow. All matched rules are reported.

Money handling

  • All amounts stored as integer minor units (e.g., USD cents).
  • Zero-decimal currencies (JPY, KRW, etc.) use 0 decimal places.
  • Conversion at API/PayPal boundaries via apps/common/money.py:
    • to_minor(amount_decimal, currency) → int
    • to_major(amount_int, currency) → Decimal

Idempotency

  • The Idempotency-Key header (1–255 printable characters) is required on POST /v1/spend-requests/.
  • The request hash includes the normalized destination, so changing the destination with the same key returns 409.
  • Replay with same key + same body: returns stored request with Idempotent-Replayed: true header.
  • Replay with same key + different body: 409 Conflict.

Audit log

  • Append-only per organization with hash chaining (prev_hash → hash).
  • Model save()/delete() on existing rows raises PermissionError.
  • PostgreSQL trigger blocks UPDATE/DELETE/TRUNCATE at the database level.
  • verify_audit management command recomputes hashes; exits non-zero on mismatch.
  • Tamper-evident, not tamper-proof (head hash not anchored externally).

Lock order

Every write path locks rows in this order:

  1. Agent (select_for_update)
  2. Policy (select_for_update)
  3. SpendRequest
  4. Approval
  5. Organization (for audit)

This prevents deadlocks and double-spend races on PostgreSQL.

CI / CD

GitHub Actions (.github/workflows/ci.yml) runs on every push and PR:

  1. backend: PostgreSQL service, ruff lint, import-linter contracts, Django checks (including --deploy), migration check, full test suite
  2. frontend: npm ci, ESLint, TypeScript build
  3. security-audit: pip-audit (Python deps) and npm audit (Node deps)

Locally, run the same checks:

cd backend && ruff check . && lint-imports && python manage.py makemigrations --check --dry-run && python manage.py test
cd frontend && npm run lint && npm run build

Code conventions

Backend (Python)

  • Ruff for linting: ruff check . (config: backend/ruff.toml)
  • Import linter: .importlinter enforces engine has no Django/app imports
  • Django 6.1 + DRF 3.18; drf-spectacular for OpenAPI generation
  • Model mutations go through service functions in services.py
  • Management commands for idempotent, cron-safe operations
  • Commit messages: type(scope): message (feat, fix, docs, chore, ci, test)
  • One branch per task; small PRs with at least one review

Frontend (TypeScript/React)

  • React 19 + TypeScript + Vite + ESLint
  • react-router v7 data router
  • UI components are framework-agnostic (no heavy UI libraries)
  • Dashboard screens use the demo store; Simulator uses the real API
