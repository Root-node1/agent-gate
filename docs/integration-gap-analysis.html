Executive summary

This analysis traces every frontend API call to its corresponding backend route. The frontend has two distinct data paths:

  1. Dashboard screens (11/17): Consume in-memory demo store (frontend/src/demo/store.ts) — zero backend calls
  2. Simulator/Live pages (3/17): Use real agent API (POST /v1/spend-requests/) via frontend/src/api/spendRequests.ts

Critical finding

The dashboard is a fully functional mock application. It replicates the backend rule engine in TypeScript but has no integration with the actual backend for any dashboard operation (approvals, policies, agents, audit, transactions, settings).

Detailed gap categories

1. Frontend screens using mock data (11 screens)

All dashboard screens read from useDemoState() which returns frontend/src/demo/store.ts state. The demo store:

  • Replicates backend rule engine in TypeScript (demo/rules.ts) — but with different rule codes and missing rules
  • Generates 2 weeks of synthetic history via buildSeed()
  • Provides submitSpendRequest()/decideApproval()/createAgent()/updatePolicy() mutators that update in-memory state
  • Never calls the backend
Impact: Dashboard works offline but shows stale/fake data. No real approvals, no real policies, no real audit trail.

4. Request/response contract mismatches

Policy list response

Backend (PolicySerializer):

{
  "id": "uuid",
  "organization": "uuid",
  "agent": "uuid",
  "agent_name": "string",
  "name": "string",
  "version": 1,
  "currency": "USD",
  "per_transaction_cap_minor": 10000,
  "daily_budget_minor": 50000,
  "merchant_rules": [{"id": "uuid", "merchant_ref": "acme.com", "kind": "allow", "note": ""}]
}

Frontend expects (Policy type in demo/types.ts):

{
  "id": 123,
  "name": "string",
  "agent_id": 456,
  "currency": "USD",
  "per_transaction_cap": 100.00,
  "approval_threshold": 50.00,
  "daily_budget": 500.00,
  "monthly_budget": 5000.00,
  "allowed_merchants": ["acme.com"],
  "blocked_merchants": ["badactor.com"],
  "updated_at": "2026-10-27T12:00:00Z"
}

Gaps:

  • PK type: UUID vs number
  • Minor units vs major units
  • merchant_rules[] vs separate allowed_merchants[]/blocked_merchants[]
  • Missing approval_threshold, weekly_budget, velocity_*, merchant_window_cap, untrusted_source_action, injection_escalate_threshold, classifier_required, approval_ttl_minutes, timezone

Audit log response

Backend (AuditEventSerializer): Flat event with prev_hash, hash, payload (JSON)

Frontend (buildRows() in auditData.ts): Transformed rows with explanation, decision, agent derived from payload

Gaps: Frontend expects pre-computed explanations and decision extraction; backend returns raw events.

Spend request detail (Dashboard vs Agent)

Backend agent view: Returns approval field (outcome string or null)

Frontend dashboard: Expects full approval object with outcome, approver, note, expires_at, decided_at

6. Missing approval state synchronization

Backend: Approval state changes (pending → approved/denied/expired) trigger:

  • SpendRequest.status update
  • AuditEvent (approval.approved/denied/expired)
  • PaymentStatus update (on approve → processing)

Frontend demo store: Mirrors this in decideApproval() but:

  • No real-time sync (other tabs/users don't see changes)
  • No WebSocket/SSE for live updates
  • Payment status simulation via setTimeout (2.5s)
Integration need: Dashboard must poll or subscribe to approval status changes.

7. Missing payment status synchronization

Backend: SpendRequest.payment_status — not_sent | awaiting_approval | processing | completed | failed

Frontend demo: SpendRequest.payment_status — not_sent | awaiting_approval | processing | completed | failed (matches!)

Gap: Frontend has no way to receive real PayPal webhook updates. Simulator shows raw response but doesn't poll for processing → completed/failed.

9. Missing loading and error states

All dashboard screens use useSimulatedLoad() which adds a fixed 300-500ms artificial delay and shows skeleton rows. Real API integration needs:

  • Per-request loading states
  • Error boundaries / toast notifications (toast context exists)
  • Retry logic for idempotent operations
  • Empty states (already implemented via EmptyState component)
