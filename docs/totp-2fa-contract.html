2. Current authentication baseline

The feat/totp-2fa branch (HEAD 986cf4a) is a descendant of feat/github-oauth, so the AUTH-01 (email/password) and AUTH-04A (GitHub OAuth) work is fully integrated. The authentication stack is built on django-allauth==65.21.0 with the Headless JSON contract. Two authentication schemes exist and must remain strictly separated:

Agent API Key (machine principal)
Authorization: Bearer agk_... via backend/apps/agents/authentication.py (AgentKeyAuthentication, authentication.py:49). A 12-character prefix is indexed and used for the initial ApiKey.objects.get(prefix=...) lookup (authentication.py:64, prefix length defined in apps/agents/keys.py); the full key is then verified with a constant-time SHA-256 hash compare (hash_matches(raw_key, api_key.key_hash), authentication.py:71). 4. Proposed MFA architecture

4.1 Framework choice: allauth.mfa, not django-two-factor-auth

The original AUTH-05 spec (see authentication-architecture.html:687 and implementation-plan.html:135) recommended adding django-two-factor-auth (built on django-otp) as a second auth library. That recommendation predates the discovery that django-allauth 65.21.0 already ships a self-contained allauth.mfa module providing TOTP + recovery codes + a Headless SPA API (verified from the wheel). Reusing it avoids running two MFA implementations in one project, which would conflict on:

  • The session model — django-two-factor-auth manages its own 2fa session keys and its own middleware; allauth mfa integrates with the existing allauth session + AccountMiddleware already on this branch.
  • URL namespace — the project mounts allauth headless at /api/auth/headless/ (config/urls.py:61); allauth mfa Headless URLs auto-attach to that same namespace, whereas django-two-factor-auth would add a parallel /2fa/ mount.
  • The import-linter contract engine-is-pure (backend/.importlinter) and the PayPal-isolation contract are unaffected either way, but a single auth framework keeps apps.accounts as the sole integration boundary.

Recommended default: enable allauth.mfa (the Tech Lead must confirm this over django-two-factor-auth — see §15 Q1). If the Tech Lead insists on django-two-factor-auth, the remainder of this section does not apply and the AUTH-05 plan must be re-derived from implementation-plan.html:135.

4.3 Custom MFA adapter — secret protection at rest

This is the single most important code decision in AUTH-05. allauth’s built-in adapter (DefaultMFAAdapter) leaves TOTP secrets on disk in cleartext: encrypt() is a no-op returning the input unchanged, so Authenticator.data (a JSONField) would store {"secret": "JBSWY3DPEHPK3PXP"} verbatim (allauth/mfa/adapter.py:106-116). A database read or a backup leak would expose every user’s TOTP secret.

The project must override the adapter (setting MFA_ADAPTER = "apps.accounts.adapters.CustomMFAAdapter") and implement at-rest encryption. The proposed shape, mirroring the existing CustomAccountAdapter / CustomSocialAccountAdapter in apps/accounts/adapters.py:14,34:

from allauth.mfa.adapter import DefaultMFAAdapter
from django.conf import settings
from cryptography.fernet import Fernet  # AES-256-CBC + HMAC-SHA256, keyed from an env-provided value

class CustomMFAAdapter(DefaultMFAAdapter):
    def encrypt(self, text):
        return get_fernet().encrypt(text.encode()).decode()

    def decrypt(self, encrypted_text):
        return get_fernet().decrypt(encrypted_text.encode()).decode()
Key source
settings.MFA_ENCRYPTION_KEY — a urlsafe_b64encode Fernet key read from the environment (e.g. MFA_ENCRYPTION_KEY=... in .env, absent from .env.example today). It must be independent of DJANGO_SECRET_KEY: a secret-key rotation currently invalidates sessions but must not silently invalidate MFA (which would force every 2FA user to re-enroll). This mirrors the existing pattern where GITHUB_OAUTH_SECRET is env-only (base.py:220).
Migration of existing secrets
Because the no-op is only in effect before deployment, any secrets enrolled during a transition window must be re-encrypted. A one-off data migration is the responsibility of AUTH-05B; the model itself does not change.
Recovery codes
Recovery codes are not stored individually. allauth derives them deterministically from a per-user seed (320-bit, secrets.token_hex(40)) via HMAC-SHA1, and tracks consumption with a used_mask bitmask (recovery_codes/internal/auth.py:28-37,44-67,69-77). The seed is persisted in Authenticator.data["seed"] and is itself passed through the adapter’s encrypt() (auth.py:32) — so the same Fernet at-rest protection that secures the TOTP secret also protects the recovery-code seed. The adapter hook therefore secures both authenticator types, not just TOTP.

Enrollment secret reaches the browser — by design

During enrollment, GET /totp returns the raw secret to the authenticated SPA (along with the otpauth:// URL) so the user can scan a QR or enter it manually into an authenticator app. This is inherent to TOTP provisioning; the secret is only persisted (and, post-4.3, encrypted) once the user submits a valid verification code. Transport confidentiality therefore depends entirely on HTTPS end-to-end (the Caddy TLS termination).

4.6 Role-based 2FA enforcement (the project responsibility)

allauth mfa is opt-in per user: it challenges users who have enrolled an authenticator, but it cannot require that a given user enroll, and it knows nothing about the project’s admin/approver roles. The acceptance criteria in authentication-architecture.html:691,698 ("2FA required for admin/approver login") therefore need a project layer on top. Proposed approach:

  1. TOTP challenge is native allauth (no project flag). When a user who has enrolled an authenticator logs in (password, §2.2, or GitHub OAuth, §7.1), the allauth LoginStageController runs resume_login() (account/internal/flows/login.py:128) → ctrl.handle() (account/stages.py:117-144). The AuthenticateStage._should_handle() (allauth/mfa/stages.py:28-39) detects the enrolled Authenticator via is_mfa_enabled() (allauth/mfa/adapter.py:124-133) and returns a redirect to mfa_authenticate; the controller then stashes the login under account_login (stash_login, account/internal/stagekit.py:65-66) and does not call adapter.login(). The user is therefore request.user.is_authenticated == False until POST /2fa/authenticate succeeds, at which point stage.exit() → resume_login → adapter.login() (login.py:140) is the only point the session is completed. The SPA observes this pending state from the login response (flows: [{"id":"mfa_authenticate","is_pending":true,...}], §7.3), not from a project-defined session key.
  2. Auth-state distinction (no parallel flag needed). There are exactly three meaningful states, all derivable from allauth primitives:
    StateDetection (source-anchored)
    MFA pending during login not request.user.is_authenticated and get_pending_stage(request) (allauth.account.internal.stagekit:17) returns the mfa_authenticate stage; headless: AuthenticationResponse.meta.is_authenticated == false plus a pending mfa_authenticate flow (§7.3).
    Fully authenticated, MFA enrolled request.user.is_authenticated and is_mfa_enabled(request.user) is True (allauth/mfa/utils.py:16).
    Fully authenticated, privileged, not enrolled (enrollment required) request.user.is_authenticated and not is_mfa_enabled(request.user) and the user holds role ε (admin, approver) (OrgMembership.Role, accounts/models.py:34).
    record_authentication() (account/internal/flows/login.py:39-52) notes the method used (password/socialaccount/mfa) but, per its own docstring, does not imply full sign-in — it is present even when the 2FA challenge later fails.
  3. Mandatory enrollment — role policy, not a session flag. allauth cannot *require* enrollment by role: it only challenges users who already enrolled. The project enforces mandatory enrollment for privileged users in two complementary, allauth-native ways:
    • Login-time (optional, UX): a custom LoginStage subclass (deriving from allauth.account.stages.LoginStage) appended to adapter.get_login_stages() (account/adapter.py:873) after AuthenticateStage (allauth/mfa/stages.py:17). For a privileged user with no enrolled Authenticator, it redirects to GET /account/authenticators/totp while the login stays stashed, so the session is never completed until enrollment succeeds. This rides the existing stage controller — it extends stash_login, it does not duplicate it with a separate flag.
    • Endpoint (authoritative): a session-based DRF permission, IsMFAEnforced, composed into IsApprover / IsOrganizationAdmin (permissions.py:27,34). It returns False when an authenticated privileged user has is_mfa_enabled(user) == False, so DRF yields 403 Forbidden with code: "mfa_enrollment_required" (see §4.9.1). The SPA intercepts that 403 and drives the enrollment flow (§12.7). IsDashboardUser (viewer) is unaffected — 2FA remains optional for viewers.
  4. Recovery flow. Allow POST /2fa/authenticate with a recovery code; allauth’s RecoveryCodes.validate_code (recovery_codes/internal/auth.py:107-123) checks the used_mask bitmask, so the same challenge endpoint accepts either a live TOTP or a recovery code.

Decision: allauth-native login stages + project role policy (no parallel flag)

The rejected design proposed a separate mfa_second_factor_required session flag toggled by a user_logged_in signal and enforced by an MFAEnforcementMiddleware returning HTTP 402. Source verification disproves both choices. (1) The user_logged_in signal fires after adapter.login() inside LoginStageController.handle() (account/stages.py:117-144; login.py:140) — i.e. after the MFA stage already succeeded — which is the wrong point to set a "pending 2FA" flag. (2) HTTP 402 has no semantic fit for an MFA gate: it is the "Payment Required" code and is not an allauth contract; the cited authentication-architecture.html:822 is superseded.

The corrected architecture reuses allauth’s own login-stage state (the account_login stash + get_pending_stage()) as the source of truth for the TOTP challenge, and a single 403 mfa_enrollment_required DRF permission (IsMFAEnforced) for mandatory enrollment of admin/approver users. There is no custom session flag, no MFAEnforcementMiddleware, and no HTTP 402. Response contract: 401 for unauthenticated / agent-key requests, 403 for an authenticated privileged user who has not yet enrolled in MFA (§4.9.1, §11.1 D16, §16 AC-06).

4.7 Session & device-trust model (v1)

Keep MFA_TRUST_ENABLED=False for AUTH-05A/05B: admin/approver users re-enter a TOTP code (or recovery code) on every login; no long-lived mfa_trusted cookie is issued. The default trust cookie, when later enabled, inherits SESSION_COOKIE_SECURE, SAMESITE, and HTTPONLY (allauth/mfa/app_settings.py:157-179) — so enabling it later is safe by default, but it widens the replay window, hence deferred.

4.8 Caching, replay, and the LocMemCache gap

allauth’s per-code replay defense (_mark_code_used → cache.add with timeout=TOTP_PERIOD, totp/internal/auth.py:114-116) depends on a shared cache. Today CACHES["default"] is LocMemCache (base.py:136-141), which is correct for the single-process dev server but broken for multi-worker Gunicorn: each worker holds an independent in-process cache, so a code accepted by worker A can be replayed to worker B. This is a deployment-blocking gap — see deployment-readiness.html:290 — and should be resolved with a shared cache (Redis) before AUTH-05 ships to production. MFA brute-force rate limiting is active via allauth’s own mechanism (see §4.8 for details; MFA_RATE_LIMITS defaults to only webauthn_login).

allauth’s MFA check_rate_limit function (allauth/mfa/base/internal/flows.py:62-76) calls ratelimit.consume(action="login_failed") via the allauth.core.ratelimit compatibility wrapper (allauth/core/ratelimit.py), which hard-codes app="allauth.account". This means MFA challenge failures are governed by ACCOUNT_RATE_LIMITS["login_failed"] (default: 10/m/ip, 5/300s/key; defined in allauth/account/app_settings.py:268-276), not by MFA_RATE_LIMITS. The MFA_RATE_LIMITS setting (app_settings.py:31-42) only governs the webauthn_login action, which is not mounted in v1 (MFA_SUPPORTED_TYPES excludes "webauthn"). Therefore:

  • Each failed MFA code attempt against POST /auth/2fa/authenticate increments the login_failed rate-limit counter for that user’s key (key=f"mfa-auth-user-{pk}").
  • After 5 failures per user within 300 seconds, the user is locked out from the MFA challenge.
  • After 10 failures per IP per minute, the IP is rate-limited.
  • On success, ratelimit.clear() is called, resetting the per-user counter.

4.9 Agent API keys are unaffected

2FA is a human dashboard control. AgentKeyAuthentication (apps/agents/authentication.py:49, Bearer agk_...) sits first in REST_FRAMEWORK.DEFAULT_AUTHENTICATION_CLASSES (base.py:160-163) and must remain first: agents are machine principals and must never be forced through a second factor. CurrentUserView already refuses agent keys (accounts/views.py:14, authentication_classes=[SessionAuthentication]). The RBAC gate for approvals/policies (IsApprover/IsOrganizationAdmin) is session-only; the agent spend path (apps.agents) continues to operate exclusively on Authorization: Bearer. No change to the agent authentication or throttling (THROTTLE_AGENT=60/min, base.py:168) is in scope.

4.9.1 DRF view-level MFA bypass prevention

The role-enforcement permission (§4.6) guards browser dashboard routes via session authentication. The DRF layer has a subtlety to defend against: the project's DEFAULT_AUTHENTICATION_CLASSES lists apps.agents.authentication.AgentKeyAuthentication (authentication.py:49) first, so DRF uses it exclusively whenever a Authorization: Bearer agk_... header is present — a machine principal must never satisfy a role gate defined by OrgMembership. The correct control is a session-based permission, IsMFAEnforced (composed into IsApprover / IsOrganizationAdmin, permissions.py:27,34) that requires both:

  • Session principal. The request authenticated via Django session (SessionAuthentication), not via AgentKeyAuthentication. An Authorization: Bearer request is handled by AgentKeyAuthentication, which returns an AgentPrincipal (authentication.py:39) that carries no OrgMembership — so the permission sees an anonymous request.user and yields 401 on role-gated views. Agent-key callers therefore cannot reach (and cannot bypass) the MFA check.
  • MFA enrolled. is_mfa_enabled(request.user) (allauth/mfa/utils.py:16; backed by Authenticator.objects.filter(user_id=...) , allauth/mfa/adapter.py:124-133) is True. For an authenticated privileged user who has not enrolled, the permission returns False and DRF yields 403 Forbidden with code: "mfa_enrollment_required"; the SPA routes to enrollment (§12.7).

The spend path (apps.agents) is intentionally agent-key-only — machine principals never pass a second factor — and is out of scope for MFA: no change to AgentKeyAuthentication or THROTTLE_AGENT=60/min (base.py:168). Sensitive, session-only actions (approval decisions, policy writes, audit-chain verification) bind IsMFAEnforced so an enrolled admin cannot sidestep the second factor with a leaked key.

Enforcement model

This is not a parallel session flag. IsMFAEnforced asks allauth directly: does the authenticated user own an enrolled Authenticator (allauth/mfa/models.py:24-50)? There is no mfa_second_factor_required session key and no separate middleware — enforcement is a single DRF permission class evaluated per request on privileged views. Because DRF selects AgentKeyAuthentication first on a Bearer request, that request never yields a User, so the permission correctly yields 401 for agent-key callers on role-gated routes. A dedicated test (test_auth_mfa_drf_bypass.py, §14.5) must verify: agent-key → 401 on IsApprover/IsOrganizationAdmin; authenticated-but-unenrolled privileged user → 403 mfa_enrollment_required.

5. TOTP cryptography and secret protection

5.1 Algorithm: RFC 4226 HOTP → RFC 6238 TOTP

allauth 65.21.0 implements TOTP in pure standard library code (no pyotp dependency — verified absent from the wheel’s Requires-Dist). The construction (allauth/mfa/totp/internal/auth.py):

  1. Secret → counter binding. hotp_value(secret, counter) (auth.py:50) packs the counter as an 8-byte big-endian integer (struct.pack(">Q", counter)), Base32-decodes the secret, and computes HMAC-SHA1. This is exactly RFC 4226.
  2. Dynamic truncation. offset = hmac[-1] & 0x0F; the 4 bytes at [offset:offset+4] are masked to 31 bits (& 0x7F) and read big-endian (auth.py:56-62).
  3. Digit reduction. value %= 10**TOTP_DIGITS then zero-padded to TOTP_DIGITS (auth.py:63-64,68). Defaults: 6 digits, 30-second step (app_settings.py:67-78).
  4. Time windowing. yield_hotp_counters_from_time() (auth.py:43) yields int(time.time()) // TOTP_PERIOD plus [-TOTP_TOLERANCE, +TOTP_TOLERANCE] counters, so MFA_TOTP_TOLERANCE=0 (finalized) accepts exactly one code per 30s window. The earlier proposal to raise to 1 was rejected by the Tech Lead; clock skew >30s is treated as an operations-layer incident, not an MFA config change.
  5. Constant-time compare. each candidate is checked with compare_user_code(actual=code, expected=...) imported from allauth/core/internal/cryptokit.py (auth.py:16,82), preventing timing oracles against the submitted code.

5.2 Secret generation & entropy

generate_totp_secret() (auth.py:25-27) produces base64.b32encode(secrets.token_bytes(20)): 160 bits of entropy (20 bytes) rendered as 32 Base32 characters. This exceeds the 112-bit minimum for symmetric authenticators (NIST SP 800-63B Â 5.1.1.2) and the 128-bit threshold widely cited for TOTP secrets (BIP-0032 / RFC 6238 guidance). secrets is the OS CSPRNG (/dev/urandom), not the random module.

5.3 Provisioning URI & QR code

On GET /totp with no existing authenticator, allauth returns a TOTPNotFoundResponse containing meta.secret and meta.totp_url (allauth/headless/mfa/response.py:62-71; emitted by ManageTOTPView.get at views.py:93-103). The URL is built by DefaultMFAAdapter.build_totp_url() (adapter.py:74-87): 

otpauth://totp/AgentGate:alice@example.com?secret=JBSWY3DPEHPK3PXP&issuer=AgentGate

The issuer defaults to the site name (get_totp_issuer, adapter.py:68-72) — should be pinned to "AgentGate" via MFA_TOTP_ISSUER for stable app naming in authenticator apps. The QR is rendered as an inline SVG by build_totp_svg() using the qrcode library (adapter.py:89-96), so no image file round-trips through the backend.

5.4 Verification, tolerance, and replay defense

validate_totp_code(secret, code) (auth.py:76-84) iterates the tolerance window; the first matching counter wins. Crucially, TOTP.validate_code (auth.py:101-109) then calls _mark_code_used(code), which does a cache.add() on key allauth.mfa.totp.used?user={id}&code={normalized} with timeout=TOTP_PERIOD (auth.py:111-116). Because cache.add is atomic-and-return-false-if-exists, each 6-digit code can be accepted at most once per 30-second window — defending against replay of a captured code within the same window. (See §4.8 for the LocMemCache multi-worker caveat.)

5.5 At-rest protection (the critical gap)

The raw TOTP secret is persisted by TOTP.activate() as data={"secret": encrypt(secret)} (auth.py:96), i.e. it passes through the adapter’s encrypt(). The built-in default (DefaultMFAAdapter.encrypt, adapter.py:106-111) is a no-op that returns the plaintext. With no override, every user’s Base32 secret is stored in cleartext inside Authenticator.data on PostgreSQL — recoverable by anyone with a DB read or a backup.

The mitigation (proposed in §4.3) is a project CustomMFAAdapter: MFA_ADAPTER = "apps.accounts.adapters.CustomMFAAdapter", overriding encrypt()/decrypt() with cryptography.fernet.Fernet (AES-256-CBC + HMAC-SHA256, authenticated). Key management:

  • Key source. MFA_ENCRYPTION_KEY from the environment (Fernet urlsafe_b64encode key). Keep it out of DJANGO_SECRET_KEY: rotating DJANGO_SECRET_KEY (already done on every new deploy via run.sh:31 / OPERATIONS.md) invalidates sessions but must not invalidate MFA — otherwise every enrolled user is forced through re-enrollment.
  • Key rotation. Fernet supports an ordered MultiFernet key list for zero-downtime rotation; rotate the MFA key independently of the Django secret.
  • Recovery-code seeds. use the same encrypt() path (recovery_codes/internal/auth.py:32), so a single adapter override covers both authenticator types.
  • Migration. No schema change is needed; any secret enrolled during the plaintext window must be re-encrypted by a one-off data migration in AUTH-05B.

5.6 In-transit & enrollment disclosure

During enrollment the raw secret is returned to the browser in the TOTPNotFoundResponse (meta.secret, response.py:67) so the user can scan a QR or type it into an authenticator app. This is inherent to TOTP provisioning — the authenticator app must receive the shared secret — and is acceptable only under TLS. The secret is stashed in the request session (SECRET_SESSION_KEY = "mfa.totp.secret", auth.py:22) and cleared on activation (clear_totp_secret, flows.py:42); it is never logged (adapters.py logging in apps/accounts/adapters.py:99 only logs social-auth errors, not TOTP secrets). The SPA must render the QR and discard the secret without persisting it client-side.

5.7 Recovery-code cryptography (backup factor)

Recovery codes are deterministic, not random: a 320-bit seed (secrets.token_hex(40), recovery_codes/internal/auth.py:41) is the sole stored value, and each of the MFA_RECOVERY_CODE_COUNT=10 codes is HMAC-SHA1(seed, i) truncated to MFA_RECOVERY_CODE_DIGITS=8 decimals (auth.py:55-66). Because the derivation is deterministic, the seed alone (encrypted via the adapter, §5.5) protects the entire set; no individual code is stored. Usage is single-use via the used_mask bitmask (auth.py:69-77), checked and mutated under a select_for_update() row lock for the validate path (auth.py:107-112). Comparison uses the same constant-time compare_user_code (auth.py:120).

5.8 Test/dev bypass (must never reach prod)

MFA_TOTP_INSECURE_BYPASS_CODE (app_settings.py:87-100) returns True for a hardcoded code — but only when settings.DEBUG is True; otherwise allauth raises ImproperlyConfigured. It is intended for E2E test fixtures only. If it ever appears in .env for a production host, allauth itself refuses to start, which is the desired fail-closed behavior.

5.9 Frontend discovery

Once allauth.mfa is installed, the headless config endpoint advertises 2FA availability to the SPA: GET /api/auth/headless/browser/v1/config returns meta.mfa = {"supported_types": [...], "passkey_login_enabled": bool} (allauth/headless/mfa/response.py:11-18, surfaced via allauth/headless/base/urls.py). The SPA can therefore gate its 2FA UI on this field rather than on a project-level TOTP_ENABLED env var — removing the need for the TOTP_ENABLED toggle from earlier planning (deployment-readiness.html:290, authentication-architecture.html:808).

7. MFA challenge during password and GitHub OAuth login

The two primary-login paths (email/password and GitHub OAuth) do not get separate MFA logic. They converge on a single allauth stage controller, so the second-factor challenge applies uniformly once allauth.mfa is enabled. This is verified from the installed source (account/internal/flows/login.py and socialaccount/internal/flows/login.py).

7.1 Login convergence point

Both flows reduce to resume_login → LoginStageController.handle().

Email / password login
LoginView.post (allauth/headless/account/views.py:142) calls flows.login.perform_password_login (account/internal/flows/login.py:106), which records method="password" and calls perform_login.
GitHub OAuth login
The GitHub callback completes in socialaccount/internal/flows/login.py:_login, which first calls record_authentication(request, sociallogin) (socialaccount/internal/flows/login.py:87-94) recording method="socialaccount" with provider & uid, then calls the same perform_login(...) (socialaccount/internal/flows/login.py:25).

perform_login (account/internal/flows/login.py:122) → resume_login (login.py:128), which constructs a LoginStageController and calls ctrl.handle() (account/stages.py:117). That iterates the stages returned by adapter.get_login_stages() (account/adapter.py:873).

7.2 When the challenge fires

get_login_stages() appends allauth.mfa.stages.AuthenticateStage when allauth_settings.MFA_ENABLED is true (account/adapter.py:879-881). The stage's _should_handle (mfa/stages.py:28-39) returns True iff all of:

  • The login has a user (self.login.user is not None).
  • The user has at least one TOTP or WebAuthn authenticator (is_mfa_enabled(user, [TOTP, WEBAUTHN]), adapter.py:124-133). Users with only recovery codes are not challenged — recovery codes are a backup, not a login gate.
  • The login did not come from a passwordless/WebAuthn login (did_use_passwordless_login returns False — a passkey login already satisfies the second factor).
  • The browser is not a trusted device (trust.is_trusted_browser returns False; this is a no-op when MFA_TRUST_ENABLED=False, the v1 default — see §4.7).

Crucially, _should_handle is based purely on enrolled authenticators, not on role. The project-level requirement that admin/approver users must enroll (and thus be challenged) is a project responsibility layered above allauth — see §4.6.

7.3 The headless challenge contract

When the stage is pending, LoginStageController.handle() stashes the login (via stash_login, account/internal/stagekit.py) and returns an AuthenticationResponse whose HTTP status stays 200 but whose flows array advertises the pending stage. The SPA discovers the challenge there: 

"flows": [
  ...
  { "id": "mfa_authenticate", "is_pending": true, "types": ["totp"] }
]

_enrich_mfa_flow (allauth/headless/base/response.py:104-111) populates types by calling adapter.is_mfa_enabled(stage.login.user, types=[typ]) for each Authenticator.Type, so the SPA learns exactly which factors the user has enrolled (e.g. ["totp"] or ["totp", "recovery_codes"]; WebAuthn is listed only when present).

The SPA then clears any "logged in" UI and renders its 2FA entry, posting the code to: 

POST /api/auth/headless/browser/v1/auth/2fa/authenticate
Content-Type: application/json
X-CSRFToken: <csrftoken>

{ "code": "<6-digit TOTP>" }

Verified handling (allauth/headless/mfa/views.py:58-65):

  1. AuthenticationStageAPIView.handle (headless/base/views.py:38-48) re-enters the pending stage via LoginStageController.enter(request, MFA_AUTHENTICATE); if no stage is pending it returns UnauthorizedResponse (401).
  2. AuthenticateInput (inputs.py:18 → BaseAuthenticateForm, mfa/base/forms.py:13-54) binds the code field. clean_code iterates all of the user's non-WebAuthn authenticators (preferring TOTP as main_auth for failure reporting), calls check_rate_limit(self.user), then auth.wrap().validate_code(code) on each until one accepts.
  3. The first accepting authenticator wins; on success post_authentication(request, authenticator) (mfa/base/internal/flows.py:46) calls authenticator.record_usage(), records method="mfa" with {"id", "type", ...} into the session auth records (account/internal/flows/login.py:55-81), and dispatches signals.authenticator_used.
  4. respond_next_stage() (views.py:52-53) calls stage.exit(), which pop_logins the stashed login and runs resume_login → adapter.login(request, user), setting the session cookie — i.e. the user is now fully authenticated. The response is an AuthenticationResponse with meta.is_authenticated: true.

Recovery codes are accepted at the same challenge endpoint

BaseAuthenticateForm.clean_code iterates all non-WebAuthn authenticators (base/forms.py:29-32), which includes the recovery_codes type. RecoveryCodes.validate_code (recovery_codes/internal/auth.py:107-123) checks the used_mask bitmask and marks the matched code consumed. So the SPA posts the same {"code": "..."} to /2fa/authenticate whether the user supplies a live TOTP or a backup code — no separate switch is needed.

7.4 Password reset and MFA interaction

Password reset (POST /auth/password/reset + email verification code) is a primary authentication factor, not a second factor. The allauth default is to log the user in on email confirmation (ACCOUNT_LOGIN_ON_EMAIL_CONFIRMATION=True), but this project explicitly sets ACCOUNT_LOGIN_ON_EMAIL_CONFIRMATION=False (base.py:200), so a user completing password reset is not automatically logged in — they must re-authenticate with their new password.

Key interaction points with MFA:

  1. No MFA challenge during reset. Password reset flow does not invoke the MFA stage controller. It is gated purely by email possession (the verification code).
  2. MFA persists across password reset. The TOTP secret and recovery-code seed are encrypted with MFA_ENCRYPTION_KEY (independent of DJANGO_SECRET_KEY, §4.3/§5.5). Resetting the password does not invalidate MFA enrollment — the user’s TOTP authenticator continues to work after password reset.
  3. Compromised password + MFA. If an attacker obtains the password (e.g. via a breach), they still cannot log in as an MFA-enrolled admin/approver without the TOTP code or a recovery code. This is the primary security benefit of 2FA.
  4. Reset of MFA itself. A user who loses their TOTP app must use a recovery code to log in, then disable and re-enroll TOTP. If all recovery codes are exhausted, an admin must manually revoke the authenticator row (§8.7).
  5. Signal: authenticator_reset fires on recovery code regeneration (recovery_codes/internal/flows.py:49), providing an audit trail for reset-related MFA changes.

7.5 GitHub OAuth specifics

After the GitHub callback's _login records the method="socialaccount" step (provider = "github"), the same LoginStageController.handle() runs. If the user has enrolled TOTP, the mfa_authenticate stage is pending and the headless login response again advertises it in flows; the user is not fully authenticated (no session cookie is set) until they complete POST /auth/2fa/authenticate. Thus a GitHub-OAuth'd admin is no weaker than a password admin: both pause at the second factor. The record_authentication session log will show socialaccount → mfa in sequence (account/internal/flows/login.py:55-81).

7.6 Reauthentication (not login)

POST /api/auth/headless/browser/v1/auth/2fa/reauthenticate (ReauthenticateView, views.py:71-77) is a separate endpoint for re-running a second factor mid-session for a sensitive action. It uses ReauthenticateInput → ReauthenticateForm (mfa/base/forms.py:62-64), the same clean_code validator, then calls post_authentication(..., reauthenticated=True), which tags the auth record with "reauthenticated": True and dispatches signals.authenticator_used(reauthenticated=True). The response is an AuthenticationResponse confirming the session remains.

8. Recovery codes and replay prevention

Recovery codes in allauth 65.21.0 are deterministic backups, not random one-shots, and are consumed through the same code path as a TOTP. Both the TOTP replay defense and the recovery-code single-use defense are verified from allauth/mfa/{totp,recovery_codes}/internal/auth.py.

8.1 Recovery-code generation — deterministic seed

RecoveryCodes.activate (recovery_codes/internal/auth.py:22-38) stores a single 320-bit seed: 

"seed": encrypt(secrets.token_hex(40))   # 40 hex chars = 320 bits

with "used_mask": 0. The seed is passed through the adapter encrypt() hook (auth.py:32), so the same Fernet at-rest protection that secures the TOTP secret (§4.3/§5.5) also covers recovery codes. Each of the MFA_RECOVERY_CODE_COUNT=10 (app_settings.py:49) codes is derived deterministically in generate_codes (auth.py:50-67): 

HMAC-SHA1(seed, f"{i:3},")  →  first byte_count bytes  →  int % 10**N  →  zero-pad
byte_count = min(RECOVERY_CODE_DIGITS // 2, sha1_digest_size)   # = 4 for 8-digit codes
N = MFA_RECOVERY_CODE_DIGITS                                        # = 8 (app_settings.py:60)

Because derivation is deterministic, the seed is the sole secret for the whole set; no individual code is persisted. Regenerating a fresh seed invalidates all prior codes (the old Authenticator row is deleted and replaced — recovery_codes/internal/flows.py:40-43).

8.2 Recovery-code consumption — single-use under lock

RecoveryCodes.validate_code (auth.py:107-123) enforces single-use:

  1. select_for_update().get(pk=self.instance.pk) takes a row lock on the recovery-codes Authenticator inside @transaction.atomic, preventing a concurrent double-spend.
  2. It checks _is_code_used(i) = bool(used_mask & (1 << i)) (auth.py:69-71), skipping already-consumed slots.
  3. Each candidate is compared with constant-time compare_user_code(actual=code, expected=c) (mfa/base/forms.py:37,base/forms.py:37), imported from allauth.core.internal.cryptokit.
  4. On match, _mark_code_used(i) (auth.py:73-77) sets the bit and save()s the mask — the same code can never validate again.

8.3 Auto-generation at TOTP activation (no email)

When TOTP is activated, activate_totp calls auto_generate_recovery_codes(request) (totp/internal/flows.py:41; recovery_codes/internal/flows.py:82-108). This creates a recovery-codes authenticator only if (a) the user is authenticated, (b) RECOVERY_CODES is in MFA_SUPPORTED_TYPES, and (c) no recovery-codes authenticator yet exists. Per its docstring, it deliberately does not send a notification email — recovery codes are created implicitly and are only disclosed via the /account/authenticators/recovery-codes view. A authenticator_added signal and a mfa/messages/recovery_codes_generated.txt warning message are fired (flows.py:98-105).

8.4 Explicit regeneration

POST /api/auth/headless/browser/v1/account/authenticators/recovery-codes (ManageRecoveryCodesView.post, views.py:138-141) takes an empty body (GenerateRecoveryCodesInput, inputs.py:30 → GenerateRecoveryCodesForm with no fields, recovery_codes/forms.py:23-34) and calls generate_recovery_codes(request) (flows.py:27-58):

  • raise_if_reauthentication_required gates the call (flows.py:28-31).
  • can_generate_recovery_codes (flows.py:18-23) requires at least one non-recovery-codes authenticator to exist — you cannot generate recovery codes for a user with no other factor.
  • Old codes row is delete()d, a new seed generated, all under @transaction.atomic with a select_for_update() user-row lock (flows.py:27,37-38).
  • On-commit: signals.authenticator_reset, the mfa/messages/recovery_codes_generated.txt message, and an mfa/email/recovery_codes_generated notification email (flows.py:47-55).
  • In the headless response, can_view=True always (views.py:141), so the new codes are returned this once.

8.5 Viewing / showing codes once

GET /api/auth/headless/browser/v1/account/authenticators/recovery-codes (ManageRecoveryCodesView.get, views.py:130-136) calls view_recovery_codes (flows.py:61-79):

  • Requires authentication (flows.py:62) and passes
  • raise_if_reauthentication_required.
  • If a recovery-codes authenticator exists, mark_as_viewed() (auth.py:125-129) stamps data["viewed_at"] = time.time() on the first access.
  • can_view = (not RECOVERY_CODES_SHOW_ONCE) or not did_view (flows.py:78; allauth default MFA_RECOVERY_CODES_SHOW_ONCE=False, app_settings.py:63; finalized V1 value: True, per Tech Lead Decision 7). With SHOW_ONCE=True, later views carry only counts, never the plaintext codes.

File download is headless-only a gap

The traditional mfa_download_recovery_codes view (mfa/recovery_codes/views.py:65-94) returns the unused codes as a text/plain attachment (Content-Disposition: attachment; filename="recovery-codes.txt", views.py:90). There is no headless equivalent: _authenticator_data (allauth/headless/mfa/response.py:21-51) exposes only total_code_count, unused_code_count, and (conditionally) unused_codes in JSON. If a downloadable backup is a requirement, it must be added as a project endpoint — allauth does not provide it.

8.6 TOTP replay prevention (cache.add gate)

TOTP.validate_code (totp/internal/auth.py:76-84) iterates the tolerance window and accepts the first matching counter. TOTP.validate_code (auth.py:101-109) then calls _mark_code_used(code) (auth.py:114-116): 

cache.add(
    f"allauth.mfa.totp.used?user={self.instance.user_id}&code={normalize_user_code(code)}",
    "y",
    timeout=app_settings.TOTP_PERIOD,   # 30s
)

cache.add is atomic-return-false-if-exists, so a 6-digit code is consumable at most once per TOTP period (30s) per user. A captured code replayed within the same window is rejected with 401 (incorrect_code). This is per-user, per-code value — the same 6 digits generated in a later 30s window get a fresh key and succeed normally. Reiterating the caveat in §4.8/§5.4: because CACHES["default"] is LocMemCache (base.py:136-141), this defense is broken for multi-worker Gunicorn — each worker has an independent in-process cache, so a code accepted by worker A can be replayed to worker B. A shared cache (Redis) is a deployment blocker before prod.

8.7 Lost-authenticator recovery policy

A user who loses their TOTP device but retains access to recovery codes can recover:

  1. Login with recovery code: At POST /auth/2fa/authenticate, submit any unused 8-digit recovery code. The user is fully authenticated.
  2. Disable TOTP: DELETE /account/authenticators/totp deactivates TOTP and removes the associated recovery-codes authenticator (§6.3). Requires reauthentication if MFA_REAUTHENTICATION_REQUIRED=True.
  3. Re-enroll: POST /account/authenticators/totp generates a new secret and new recovery codes.

No recovery codes remaining:

  • The user cannot satisfy the MFA challenge at login. If they are enrolled in MFA, the mfa_authenticate stage (native allauth, §4.6) holds the login stashed and the session is never completed. If they are an admin/approver who is not enrolled, password login completes but the IsMFAEnforced permission on privileged endpoints yields 403 mfa_enrollment_required (§4.9.1), so the dashboard is reached only after (re)enrolling a second factor.
  • Admin intervention required: A superuser (or support agent) with database access must delete the user’s Authenticator rows. This must not be treated as an unrestricted procedure: the action must be logged in apps.audit with the acting admin’s identity and justification, and confirmed via a separate out-of-band support channel before execution.
  • Proposed management command: python manage.py mfa_reset_user <email> — deletes all Authenticator rows for the user and notifies them via email; prefer this over raw SQL or Django shell.

Not automated in v1

There is no self-service "I lost my phone" flow in v1. Lost-authenticator recovery requires either a spare recovery code or a superuser intervention. A self-service recovery flow (e.g. email-based MFA reset with additional verification) is deferred to v2.

10.3 Compatibility notes — why stay headless

The two contracts are mutually exclusive in routing and differ in three ways that matter to this SPA-first project:

CSRF vs. session
Traditional form views rely on Django’s cookie CSRF + HttpResponseRedirect on success. The headless contract uses X-CSRFToken + JSON (respond_next_stage, base/views.py:52-53). Mixing the two on the same login path is untested and would race the stash_login session state (account/internal/stagekit.py:60-64).
Challenge signalling
Headless surfaces the pending MFA stage via the flows array on the login response (headless/base/response.py:66-77), a pure-JSON contract the SPA polls. Traditional views redirect to mfa_authenticate (a server-side HttpResponseRedirect, stages.py:25), requiring a full page navigation — incompatible with the SPA’s client-side router.
Code disclosure
The traditional mfa_download_recovery_codes view (recovery_codes/views.py:65-94) returns plaintext codes as a file download (Content-Disposition: attachment). The headless contract never returns individual plaintext codes to the SPA via a download endpoint — only unused_codes in the JSON body of GET /account/authenticators/recovery-codes (response.py:42-43), gated by can_view. If a file download of codes is ever required headless-side, it must be a new project endpoint — do not mount the traditional view, as it bypasses the can_view JSON gating.

Recommendation

Do not add a path("mfa/", include("allauth.mfa.urls")) mount in config/urls.py. The Headless contract already covers enrollment, challenge, recovery, reauthentication, and (via §4.6) the projected role gate. Mounting the traditional tree would duplicate routes, surface a competing form-based reset surface, and require the allauth mfa/*.html templates — none of which the SPA can consume.

  1. Resolve the cache gap before production. CACHES["default"] is LocMemCache (base.py:136-141), which breaks allauth’s per-code replay defense for multi-worker Gunicorn.   2.   3. Recovery-code length reconciled. Q3 is APPROVED: 8 digits (allauth default). The earlier 20-character spec (authentication-architecture.html:699, implementation-plan.html:140) was rejected. Longer codes (more digits) remain available via MFA_RECOVERY_CODE_DIGITS if needed in a future revision; a 20-character format would imply a custom adapter override.
  4. Plan MFA key rotation. Use cryptography.fernet.MultiFernet to rotate MFA_ENCRYPTION_KEY with zero downtime. Document the rotation playbook in OPERATIONS.md and store the key in a secrets manager (the same mechanism used for GITHUB_OAUTH_SECRET).

  7. Consider MFA trust for v2. MFA_TRUST_ENABLED=False is the v1 default. If admin UX warrants a "remember this device" flow, enable it and ensure the mfa_trusted cookie inherits SESSION_COOKIE_SECURE (it does by default, §4.7). Document the widened replay window this introduces.
  8. Set up brute-force alerting on login_failed. allauth’s MFA check_rate_limit fires signals.authentication_failed on each failed challenge. Alert on bursts of MFA challenge failures, which indicate either a targeted attack or a user lockout situation.

12. Frontend handoff requirements

The SPA consumes TOTP 2FA entirely through the Headless JSON contract (/api/auth/headless/browser/v1/). No traditional template-form endpoints are mounted, so the frontend handoff is a pure REST+CSRF+session contract. This section enumerates what the frontend must implement, keyed to the backend contracts in §6--9.

12.1 CSRF bootstrap (already implemented)

The SPA already performs the CSRF bootstrap (verified by backend/tests/test_auth_signup_login.py). On app init, call GET /api/auth/headless/browser/v1/config to obtain the csrftoken cookie, then echo it as the X-CSRFToken header on every state-changing request. This is unchanged by 2FA but must extend to the MFA endpoints.

12.2 MFA discovery on the config and session endpoints

GET /api/auth/headless/browser/v1/config returns meta.mfa ({"supported_types": [...], "passkey_login_enabled": bool}, §5.9). The SPA uses this to decide whether to render 2FA UI at all. After login, the session endpoint (GET /auth/session) advertises a pending mfa_authenticate flow in its flows array when a second factor is required.

12.3 Login challenge UI

Both primary login paths (email/password §2.2, GitHub OAuth §7.1) converge on the same allauth stage controller. The handshake is:

  1. The SPA posts credentials (POST /auth/login or the GitHub redirect completes).
  2. Headless login responds with 200 OK + flows: [..., { "id": "mfa_authenticate", "is_pending": true, "types": ["totp"] }]
  3. The user has not received a session cookie yet — they are in the "pending 2FA" state.
  4. The SPA renders the 2FA entry, accepts a 6-digit TOTP or a recovery code in the same field, and posts:
POST /api/auth/headless/browser/v1/auth/2fa/authenticate
Content-Type: application/json
X-CSRFToken: <csrftoken>

{ "code": "<6-digit TOTP or 8-digit recovery code>" }
  1. On success (meta.is_authenticated: true), the session cookie is set and the user reaches the dashboard.
  2. On failure (incorrect_code), the SPA shows an inline error and allows retry. Repeated failures trigger allauth’s built-in rate limiting via ACCOUNT_RATE_LIMITS["login_failed"] (5 failures per user in 300s), with django-axes (AUTH-06) as additional defense-in-depth (§4.8).

No GET-based challenge poll

GET /auth/2fa/authenticate returns 405 Method Not Allowed (AuthenticateView defines no get, §7.3 unverified). The pending challenge is discovered only through the login flows array. The SPA must not implement a polling loop against GET /auth/2fa/authenticate.

Critical: never persist the enrollment secret client-side

During step 1, meta.secret exists in memory for QR rendering only. The SPA must not write it to localStorage, sessionStorage, or cookies. The server clears it from the session on activation (clear_totp_secret, §6.2). Transport confidentiality depends entirely on HTTPS (Caddy TLS termination).

12.5 Recovery codes UI

GET /account/authenticators/recovery-codes returns total_code_count, unused_code_count, and (if can_view) unused_codes as a JSON array (§8.5). The SPA:

  • Displays the codes once in a modal with a "copy to clipboard" button.
  • Never sends codes back to the server (they are submitted only as { "code": "..." } to /auth/2fa/authenticate during login or reauthentication).
  • The POST /account/authenticators/recovery-codes endpoint (empty body) regenerates — a destructive action the SPA should gate behind a confirmation + reauthentication.

No headless file download

The traditional mfa_download_recovery_codes view (recovery_codes/views.py:65-94) returns a .txt attachment, but it is not available on the headless contract (§8.5). If a downloadable backup is required, the SPA must assemble it client-side from the unused_codes JSON array — do not attempt to mount the traditional view (it bypasses the can_view JSON gating, §10.3).

12.6 Reauthentication for sensitive actions

For any operation gated by IsApprover or IsOrganizationAdmin, the SPA may call: 

POST /api/auth/headless/browser/v1/auth/2fa/reauthenticate
X-CSRFToken: <csrftoken>

{ "code": "<6-digit TOTP or recovery code>" }

A 200 response with AuthenticationResponse confirms the session remains and the sensitive action may proceed. A 401 means reauthentication failed — the action is rejected.

12.7 Role-based enrollment enforcement (SPA behavior)

allauth challenges users who have enrolled an authenticator at login, but it does not force enrollment, and it knows nothing about the project’s admin/approver roles. The project layer (§4.6) enforces mandatory enrollment through the IsMFAEnforced permission: an authenticated privileged user who has not enrolled receives a 403 with code: "mfa_enrollment_required" from the protected dashboard endpoint. The SPA must:

  1. Intercept the 403 mfa_enrollment_required response on dashboard routes (distinguished from a 401, which means "not logged in" → send to login).
  2. Render the TOTP enrollment flow (§12.4) as mandatory — the user cannot dismiss it or reach the dashboard until POST /account/authenticators/totp succeeds and the authenticator is persisted.
  3. Only grant dashboard access after the enrollment response confirms an active TOTP authenticator (verify via GET /account/authenticators).
  4. For viewer-role users: no enforcement gate; 2FA remains optional.

A privileged user enrolled in MFA is never in this state — the native mfa_authenticate challenge is resolved at login (§7.3) before the dashboard is reachable, so the SPA never sees the enrollment-required 403 for them. The 403 only fires for the narrow "logged in, privileged, not yet enrolled" case, which is exactly the users the Tech Lead decision (Force on next login, §15 Q10) targets.
