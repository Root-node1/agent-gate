Purpose and scope

This document specifies the recommended authentication architecture for AgentGate. It covers email/password signup and login, GitHub OAuth login, email verification, secure logout, password reset with expiring single-use links, password change, TOTP-based two-factor authentication (2FA) with recovery codes, 2FA enforcement for administrators and payment approvers, second-factor verification after both password and GitHub login, Django-managed sessions, CSRF protection, organization-scoped RBAC, and authentication rate limiting.

Ownership boundary: A dedicated auth developer owns this work. The auth developer must not modify the policy engine (backend/engine/), the spend service (backend/apps/spend/services.py), or the approval service (backend/apps/approvals/services.py). Changes are limited to backend/apps/accounts/, backend/config/urls.py, backend/config/settings/*.py, backend/requirements.txt, and the frontend session/auth layer (frontend/src/session/, frontend/src/App.tsx).

Existing frontend session layer

The current SessionProvider (frontend/src/session/SessionProvider.tsx) stores an agent API key in memory only (for the simulator) and provides a recent array of spend requests. It does not perform any dashboard-user authentication. The context.ts type (frontend/src/session/context.ts) mirrors this: it holds agentKey, setAgentKey, recent, and remember. Why not JWT

The recommended approach uses Django session cookies, not JWT. Rationale:

  • The dashboard is a server-rendered-style SPA behind the same origin; cookies work seamlessly with SameSite and Secure flags.
  • django-allauth is built around Django sessions; JWT would require a separate token store, refresh logic, and CSRF-equivalent thinking anyway.
  • Session revocation is immediate (delete the session row); JWT revocation requires a blocklist.
  • The agent API continues to use Bearer keys separately; adding JWT would create a third auth scheme for no benefit.

A second auth system or JWT is not approved for this project unless a specific, approved architectural reason requires it (e.g., a third-party B2B integration needing token exchange).

Session contract

Cookies
  • sessionid — Django session cookie. Secure, HttpOnly, SameSite=Lax (configurable to Strict if same-origin).
  • csrftoken — Django CSRF cookie. Secure, HttpOnly (or readable by JS for header injection), SameSite=Lax.
Frontend cookie handling
All fetch() calls to the dashboard API must include credentials: "include" so the browser sends session and CSRF cookies. For state-changing requests (POST, PATCH, DELETE), the frontend must include the X-CSRFToken header with the value from the csrftoken cookie.
CSRF exemption
The agent API (POST /v1/spend-requests/) uses AgentKeyAuthentication and must remain CSRF-exempt (it does not use SessionAuthentication). All dashboard endpoints using SessionAuthentication must enforce CSRF.

Backend permission enforcement

The backend already enforces role-based access via permission classes in backend/apps/accounts/permissions.py. The auth developer must ensure that django-allauth integration does not bypass these checks. Specifically, after a user authenticates via allauth, a post_authenticate or user_logged_in signal handler should ensure the user has at least one OrgMembership. If not, the user should be blocked from accessing dashboard endpoints (403) until an admin assigns them to an organization.

Organization assignment for new users

When a user signs up via email/password or GitHub OAuth, they must be assigned to an organization with a role. The recommended approach:

  1. Single-tenant demo: New users are auto-assigned to the organization named in DEMO_ORG_NAME (default: demo) with the viewer role. An admin later promotes them.
  2. Multi-tenant with invite codes (planned for post-MVP): User enters an invite code during signup; the backend looks up the organization and assigns the role specified by the invite.

GitHub OAuth callback flow

The django-allauth socialaccount app handles the OAuth 2.1 flow as follows:

  1. User clicks "Sign in with GitHub" on the frontend. The button links to /accounts/github/login/.
  2. Backend redirects to GitHub: Allauth stores a state nonce in the session, then redirects to https://github.com/login/oauth/authorize with client_id, redirect_uri, scope, and state.
  3. User consents on GitHub: GitHub prompts for authorization.
  4. GitHub redirects back to /accounts/github/login/callback/ with code and state.
  5. Allauth verifies state: Compares the nonce against the session. If mismatch, returns 403.
  6. Allauth exchanges the code: Server-side POST to https://github.com/login/oauth/access_token with client_id, client_secret, and code. The secret never reaches the browser.
  7. Allauth fetches user info: Server-side GET to https://api.github.com/user using the access token. Optionally fetches the user's email from /user/emails.
  8. Allauth creates/updates SocialAccount: If the GitHub user has not logged in before, a new User and SocialAccount are created. The user is then auto-assigned to the demo organization as a viewer.
  9. Allauth sets the Django session: django.contrib.auth.login() is called, which sets the sessionid cookie.
  10. Redirect to frontend: Allauth redirects to SOCIAL_AUTH_LOGIN_REDIRECT_URL (default: /accounts/profile/), which the auth developer should configure to redirect to a frontend route (e.g., https://app.agentgate.dev/dashboard).
  11. Frontend calls /api/auth/user/: Using the session cookie, the frontend verifies the user and loads their memberships and roles.
Important: The client_secret is used only server-side. It must never appear in Vite environment variables or be bundled into the frontend. All OAuth code exchange happens in the Django backend.

GitHub OAuth signup flow

Unlike some providers, GitHub always returns a user profile for any authenticated session. Allauth treats the first login as a "signup": if no SocialAccount exists for the GitHub UID, allauth creates a new User. If email verification is enabled, the user receives a verification email before the account is fully active. The ENABLE_SIGNUP_FORM setting controls whether allauth shows a signup form to collect additional fields (e.g., team name).

Frontend authentication integration

The auth developer (or frontend team in coordination) must update the following:

SessionProvider update

The SessionProvider (frontend/src/session/SessionProvider.tsx) must be extended to hold dashboard-user auth state alongside the existing agent key:

  • user — the current user object from GET /api/auth/user/
  • userLoaded — boolean; false until the /user endpoint has been polled
  • agentKey — retained for the simulator (agent-key auth path)
  • recent — retained for the simulator's local request history

Authenticated route guards

In frontend/src/App.tsx, the /app/* routes must be wrapped in an auth guard that:

  • If userLoaded === false, show a loading spinner (do not render dashboard screens).
  • If userLoaded === true and user === null, redirect to /login.
  • If userLoaded === true and user exists but has no memberships, redirect to a "waiting for admin" page.
  • Role-based sub-guards: if the user lacks approver/admin role, redirect away from /app/approvals and /app/settings.

Login page

A new /login route should present email/password login and a "Sign in with GitHub" button (which links to /accounts/github/login/). This page is outside the /app layout so unauthenticated users see it.

Logout

The logout button in AppLayout.tsx must call POST /api-auth/logout/ with a CSRF token, then call GET /api/auth/user/ to confirm the session is cleared, then redirect to /login.

Do not modify frontend/src/api/spendRequests.ts (the agent API client). The agent key auth path must remain untouched. Only the session/auth layer should change.

Authentication task breakdown (AUTH-01 through AUTH-06)

Each task below is an independent, well-scoped unit of work with clear acceptance criteria and a verification command. Tasks must be implemented in dependency order. Implementation is out of scope for this phase — this is the task decomposition for future implementation.

AUTH-01 — Email/password signup and login

Dependencies: None

Owner: Backend developer

Requirements:

  • Add django-allauth and django-allauth[social] to requirements.txt
  • Configure allauth in settings/base.py:
    • Add allauth.account, allauth.socialaccount to INSTALLED_APPS
    • Add AllauthMiddleware
    • Configure ACCOUNT_EMAIL_VERIFICATION = "mandatory"
  • Create custom AccountAdapter restricting email domains to allowlisted org domains
  • Implement GET /api/auth/user/ endpoint returning user, orgs, roles, and 2FA status

Acceptance criteria:

  • Users can sign up with email + password via POST /accounts/signup/
  • Account is created inactive until email verification
  • Login via POST /accounts/login/ works for verified users
  • Unverified users cannot log in
  • Domain restriction blocks non-allowlisted emails

Verification command:

pytest tests/test_auth_signup_login.py -v

Dependencies: AUTH-01

Owner: Backend developer

AUTH-05 — TOTP two-factor authentication

Dependencies: AUTH-02

Owner: Backend developer

Requirements:

  • Add django-two-factor-auth to requirements.txt
  • Implement TOTP enrollment: generate secret, QR code, verify 6-digit code
  • Generate 10 single-use recovery codes per user
  • Enforce 2FA for admin and approver roles
  • Second-factor verification required after both password and GitHub login for 2FA-enrolled users
  • Add GET /api/auth/user/ response includes two_factor_enabled boolean

Acceptance criteria:

  • Users can enroll TOTP via QR code scan
  • TOTP verification required for admin/approver login
  • Recovery codes are 10 single-use backup codes (20 characters each)
  • 2FA can be disabled only after successful re-authentication
  • Non-admin/approver users are not forced into 2FA (opt-in)

Verification command:

pytest tests/test_auth_2fa.py -v

AUTH-06 — Organization-scoped RBAC and rate limiting

Dependencies: AUTH-05

Owner: Backend developer

Requirements:

  • Implement organization auto-assignment on signup/login via signal handler (matching email domain to org)
  • Implement permission classes:
    • IsDashboardUser — any authenticated user with at least one OrgMembership
    • IsApprover — user with admin or approver role
    • IsOrganizationAdmin — user with admin role
  • Implement authentication rate limiting:
    • DRF throttle: 5 failed login attempts per IP per 15 minutes
    • Account lockout after 5 failures for 15 minutes
    • Per-user throttling: 60 requests/minute after auth
  • Add django-axes or equivalent brute-force protection

Acceptance criteria:

  • User is auto-assigned to organization based on email domain
  • Admin in org A cannot access approvals in org B
  • Viewer role cannot approve/deny requests
  • Brute-force login attempts are blocked after 5 failures (15-minute lockout)

Verification command:

pytest tests/test_auth_rbac.py -v && pytest tests/test_auth_rate_limit.py -v
